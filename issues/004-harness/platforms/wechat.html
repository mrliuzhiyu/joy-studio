让 AI 真正能干活的不是模型，是 harness

Harness 这个英文单词，本义是"马具、鞍具"——就是套在马身上那一整套缰绳、笼头、鞍子，让骑手能驾驭一匹马的装备。

放到 AI 语境里，意思几乎一模一样：给 AI 模型这匹"野马"套上一整套装备，让它变得可控、可用、能干活。

2026 年 4 月，Anthropic 同时在跑五个独立产品：Claude.ai、Claude Code、Cowork、Design、Computer Use。

底层只有一个模型，Claude Opus 4.7。同样的权重，同样的 API。同一句话给这五个产品，做出来的是五件完全不同的事。

让同一颗大脑变成五套不同产品的，就是外面那套装备——harness。

中文圈对这个词最大的误读，是把它当成 LangChain 的某种进化版。这篇写的就是为什么不是。

01

一个模型，五种 Claude

Claude.ai 给你一段文字答复。

Claude Code 直接读你的 repo、改你的文件、跑你的测试。

Cowork 把任务拆给一组虚拟同事并行执行。

Design 把对话变成可交互的 UI 原型。

Computer Use 接管你的鼠标和键盘自己点。

同一个 Opus，五件不同的产品。差异不在模型权重，模型权重五家都一样。差异在 harness 那一层——管 context、暴露工具、划权限、决定什么时候问用户、什么时候自己干、出错怎么恢复。

不止 Anthropic 这么干。Cursor、Cognition Devin、Aider、OpenAI Codex CLI、Cline，过去一年里冒出来的 AI 编程产品都是这个结构。底层模型从那几家厂商买，差异化全在外面那层 harness。

HumanLayer 跑过一组实测：同样的 Claude Opus 4.6，跑在 Claude Code 里 Terminal Bench 2.0 排第 33；换到一套未参与 post-training 的简洁 harness 后，同模型同任务直接到第 5。模型没换，排名跳了 28 位。

02

agent 生态里 5 个不一样的位置

回到开头那个鞍具的比喻。中文圈最常见的混淆，是把这套装备当成做装备的工厂——LangChain、Mem0、LangGraph 这一类。混淆的根源是中文圈博客里这些东西经常被笼统叫做 "agent 框架"。

实际上至少分成 5 个位置完全不同的工具。

① harness（成品 agent 应用）：Claude Code、Cursor、Devin、Aider、OpenAI Codex CLI。已经做完所有产品决策——用什么 system prompt、提供哪些工具、怎么管 context、什么时候问用户、怎么记忆。下载下来直接能用。

② agent framework（写 agent 的库）：LangChain、LangGraph、AutoGen、LlamaIndex。给开发者一套抽象（Chain、Agent、Tool、Memory、Graph、Node、Edge），拿来拼装自己的 agent 应用。本身不是产品，是积木。

③ agent SDK / runtime（写 harness 的中间件）：Claude Agent SDK、Vercel AI SDK、Mastra。介于 framework 和 harness 之间——比 framework 轻、比 harness 灵活，主要给做垂直 harness 的人用。

④ memory layer（被独立出来的记忆组件）：Mem0、LangMem、Letta（前 MemGPT）。原本是 harness 内部的一个组件，因为跨 harness 同步的需求强，逐渐被独立成中间件，不绑定具体 harness。

⑤ multi-agent orchestrator（多 agent 协作模式）：LangGraph、CrewAI、OpenAI Agents SDK、AutoGen。多个 agent 之间怎么协作的模式，可以嵌入 harness 也可以独立用。侧重的是流程图，不是单 agent 的执行壳。

这 5 种东西，给谁用、用在哪、决策密度都不一样。混在一起说成 "agent 框架" 是中文圈博客的省事说法，但选型时这 5 类是 5 个完全不同的购物清单。

用前端类比这 5 种位置：harness 像 Notion / Linear / Figma——成品产品；framework 像 React——写应用的库；SDK / runtime 像 Next.js / Vercel——介于库和成品之间的中间层；memory layer 像 Auth0 / Clerk——被单独抽出来的垂直组件。orchestrator 这种多 agent 协作模式在前端里没有干净对应物，类比让位于事实——它就是 "几个 agent 之间怎么交班" 的那套规则。

完整层级画出来是这样：

用户                    ← 敲键盘的你
  ↑
harness 层              ← Claude Code / Cursor / Devin / Aider（成品）
  ↑
framework 层（可选）    ← LangChain / LangGraph / Vercel AI SDK / Mastra
  ↑
API 层                  ← Anthropic / OpenAI / Google API（HTTP 接口）
  ↑
模型层                  ← Claude Opus / GPT-5 / Gemini（厂商训出来的权重）
  ↑
硬件层                  ← GPU / TPU

熟悉操作系统的话，更精确的对应是：模型像 CPU，API 像系统调用，framework 像 libc 这类系统库，harness 像 macOS / Windows / Linux 操作系统本身。你日常用的是 macOS 这一层，CPU 在底下你看不见。

LangChain 在第 4 层。Claude Code 在第 5 层。层级搞错才是最大的混淆来源。

理论上 framework 可以用来写 harness。但 production 级 harness 几乎都不用。

Claude Code 是 Anthropic 自己写的 50 万行 TypeScript，不基于任何第三方 agent framework。Cursor 自研整个 agent loop。Aider 是 Paul Gauthier 一个人写的纯 Python，仓库里没有 langchain 依赖。

Anthropic 在 2024 年 12 月那篇官方博客《Building Effective Agents》里直接给过建议：做 agent 应用先直接调 LLM API 写，很多模式几行代码就能实现；框架能让你快速起步，但到 production 阶段不要犹豫减少抽象层、回到基础组件来搭。

理由也直接写在博客里：通用框架那层抽象在 production 上反而成了噪音。debug 时你不知道 LangChain 内部在哪一层把你的 prompt 改了什么、把模型的输出怎么解析了，结果你 debug 的不是自己的 agent，是框架本身。

LangChain 火的两年是 2023 到 2024，大量 demo 项目基于它。到 2025 年这股风变了，做严肃 agent 产品的团队普遍开始绕开它。LangChain 自己也在调整定位——2025 下半年发的博客《Your harness, your memory》开始用 harness 这个词，把自己往 harness 中间件方向挪。

framework 是积木，harness 是房子。两件事。

03

同一个 Opus，77 vs 93 分

Matt Mayer 在 thoughts.jock.pl 上有一组 2026 年 4 月做的实测对比，给了同模型 / 不同 harness 的差距一个具体数字。

同样的 Claude Opus，跑在 Claude Code 里 77 分，跑在 Cursor 里 93 分。同一个模型同一个任务，仅仅 harness 不同，差了 16 分。

同一组 CORE-Bench 数据更夸张：同样的 Claude Opus，在最简 scaffold 下 42 分，进 Claude Code 完整 harness 后 78 分。差了 36 分。

Cursor 在 2026 年 4 月公开过自家 harness 的演化史，里面有几条具体细节：

根据当前任务动态决定塞哪些文件进 context，不是把整个项目灌进去；同时支持 OpenAI 的 patch 编辑格式和 Anthropic 的字符串替换格式，对不同模型用不同的 prompt 策略；工具调用成功率跑到 99% 以上；对话中切到新模型时 harness 自动适配新模型偏好的 prompt 格式，不需要用户手工改 system prompt。

每一条都是几个工程师季度级的活，攒了一年。LangChain 这种通用框架不会给你这些，它只能给你抽象。

到 production 阶段，你要的是细节。

04

production 团队真正在抠的三件事

把 harness 拆开看，里面真正难的是三件事：context 管理、工具系统、权限边界。

先讲 context 管理。

给 Claude Code 一个项目让它修 bug，它要读你的源码、依赖、测试、之前的对话历史、system prompt 里的工具定义。加起来很容易超过 token 窗口。

超过窗口就不能跑。harness 这层要决定保留什么、压缩什么、丢什么。Claude Code 的做法叫 auto-compaction：对话长度逼近窗口上限时，自动把历史对话压缩成摘要，腾出空间给新内容。

这件事看起来自动，底下是大量产品决策——什么时候触发压缩、压到什么粒度、保留哪些片段不能丢、压缩后的摘要怎么塞回 system prompt。每个决策都直接影响用户体验。同模型同任务，压缩策略不同的两套 harness，长任务的表现能差一倍。

第二件，工具系统。

harness 决定给模型暴露哪些工具：read_file、write_file、run_bash、grep、git_commit……每多一个工具是一种新能力。但暴露太多工具，模型会乱选。Claude Code 的工具清单经过严格筛选，每一个都是用户实际高频用到的。

第三件也是最难的，权限边界。哪些工具可以静默执行，哪些必须先问用户。

Claude Code 的处理：read_file 默认静默；write_file 默认要确认；run_bash 看命令——常见的 ls、cat 静默，但涉及 sudo、rm、网络请求的会先问；git_commit 必须确认。

这套规则没写在模型里，是 harness 配置的。换个 harness 同一个 Opus 的行为完全不一样。Devin 默认在虚拟机里跑、所有命令静默执行。Cursor 把确认提到编辑器侧、用户用键盘快捷键批准。Aider 走 git-first 路线、每个改动一个独立 commit、用户随时回滚。

同一个权限问题，四种产品哲学，四套实现。选 harness 本质上是在选这种产品哲学，跟选模型不是一回事。

Anthropic 在 2026 年 3 月那篇 harness design 博客里有一句被反复引用：harness 里每一个组件，都对应一个关于"模型还做不到什么"的假设。

模型不能自己管 context，所以 harness 加了 auto-compaction。模型不能自己判断哪些命令危险，所以 harness 加了权限边界。模型还会偶尔把 JSON 写错，所以 harness 加了重试逻辑。

这套东西不像数据库或者操作系统那样有几十年理论积累。它是过去一年里被 production 事故反推出来的工程产物——用户的 API key 被硬编码进前端，于是有了密钥扫描；Claude 把生产数据库当成测试库 drop 了一次，于是有了危险命令二次确认；用户不读 AI 写的代码，于是有了代码审查机制。每一项背后都有一个真实事故。

05

五年后这个词大概率会被换掉

harness 是这一年踩坑反推出来的临时产物。模型还在变强。等模型有一天能自己处理 context、自己判断危险命令、自己规划任务，harness 这一层迟早会被部分吞掉。

部分会被吞，整层不会。

先看哪些已经在被吞。Claude 在 2026 年 3 月把 1M token context 推到 GA。Gemini 2.5 已经稳定支持 2M token context。GPT-5.4 是 400K。原本 harness 层的 auto-compaction 在长 context 模型上压力小很多——你聊到 30 万 token 时 Claude 1M 还能直接读完整对话，不需要 harness 强行压缩。

原本属于 harness 的工具调用能力也在被训练进模型本身。现代模型在训练时被特意训练得懂工具调用的格式，很多以前 harness 要做的格式纠错和重试，模型自己已经能避免了。

Karpathy 2023 年在 Microsoft Build 那次 State of GPT 演讲里给过一个长期判断：大模型应该被理解成新一代操作系统的内核进程，模型本身就该编排输入输出、调度代码解释器、调度浏览器、调度文件系统。这个想法他后来叫 LLM OS。这个视角下 harness 不是独立层，是模型功能未成熟前的临时拐杖。

但完全吞掉的那天不会到来。

Anthropic 在 2025 年下半年那篇 context engineering 长文里有一句核心论点：context 管理不是模型问题，是工程问题。模型再大，你也得决定哪些 token 该进 context、哪些不该进、它们的顺序怎么排、彼此之间的依赖怎么暴露。这件事不会因为 context 窗口变大消失，只是从"节省窗口的优化"变成"构建窗口的设计"。

历史里有个直接类比：CPU 和 OS 的关系。

八十年代有人预测 CPU 越来越强、OS 这一层会被吞掉。结果四十年下来 CPU 性能涨了几千倍，OS 没消失，反而抽象层不断往上升：从 DOS 到 Windows、到 macOS、到 iOS、到容器、到 serverless。每一代 OS 都把上一代的麻烦事吞进去，然后给上层暴露新的抽象。

harness 大概率走这条路。这种升级已经有具体信号——Anthropic 在 2025 年 9 月把 Claude Code SDK 改名 Claude Agent SDK，把"Code"这个特定场景去掉、扩张成通用 agent 工具包。Mastra、Vercel AI SDK 这种新一代 TypeScript 工具包直接把自己定位成 agent runtime，不再叫 framework，叫 runtime。词在变。

五年后 harness 这个词大概率不再是默认叫法。它可能改叫 agent runtime、agent OS、AI middleware、agentic platform……名字会换。

但这层壳要解决的问题不会消失：上下文怎么管、工具怎么暴露、权限怎么划、错误怎么恢复、记忆怎么维持、人和 agent 怎么交接。

工作不会消失，会改名字。抽象层会往上挪。

06

写 harness 是新的写代码

同一个 Opus 跑出五套不同的产品，差异化全在外面那层 harness。这件事对从业者意味着工种在重排。

prompt engineer 这个 2023 到 2024 年最火的 AI 头衔，正在退潮。国外 SolidAITech 2026 年 4 月那篇标题就是《提示词工程师这个岗位已经死了——2026 年谁在替代它》。国内 InfoQ 王一鹏 2025 年 5 月做过一组用人单位实访，结论是提示词工程师并不是当年宣传的低门槛香饽饽。学信网下面的学职平台同期也发过《提示词工程师为何遇冷？》。国内国际两边同时被宣告退潮，已经是结论性事实。

替代它的工种叫 AI engineer 或 agent engineer。LinkedIn 2026 年增长最快岗位榜单（美国版）把 AI engineer 列为榜单内年增长最快岗位之一。世界经济论坛援引 LinkedIn 数据：2023 到 2025 三年全球新增 130 万 AI 相关岗位，AI engineer 这一个头衔贡献了 7.5 万。

表面看是岗位内部洗牌，底下是能力位移。

prompt engineer 的核心能力是给一个固定的模型写出能让它表现好的 prompt。这个能力今天大模型自己都能做了——你直接问 Claude 怎么 prompt 自己解决这道题，它会给你一份很好的 prompt。这一层被模型自己吃掉了。

AI engineer 的核心能力是把模型放进一个可控、可复用、可扩展的系统里。这个系统就是 harness。

会写 harness 的人正在替代只会调 prompt 的人。

下一年红利集中在垂直 harness。

通用 harness（Claude Code、Cursor、Devin）已经被巨头占满。但每个垂直行业都需要为自己的具体场景定制 harness。医疗 harness 要懂 HIPAA 合规、电子病历格式、临床决策的责任边界。法律 harness 要懂判例引用规范、客户保密、律师工作流。教学 harness 要懂学生进度跟踪、作业引导而不是答案给出。设计 harness 要懂 Figma 协议、版式规则、品牌一致性。

这些 harness 不能从 Claude Code 一键迁移。每个都要从底下重写。

红利窗口比 SaaS 时代窄。垂直 SaaS 当年用了 5 到 8 年才把大行业占满。AI 工具的扩张节奏明显更快——Claude Code 从内部工具到 50 万行 TypeScript GA 用了 18 个月，Cursor 从编辑器插件到独角兽不到两年。垂直 harness 的窗口大概率压缩到两到三年，2026 到 2028 是入场期。

具体到现在该用什么 harness，按背景画像分。

轻装试水，从 Claude Code 开始。开箱即用、文档全、生态最成熟。

写代码为主，Claude Code、Cursor、Codex CLI 三选一。Claude Code 命令行优先、Cursor 编辑器优先、Codex CLI 轻量。

想自己写垂直 harness，Claude Agent SDK、Vercel AI SDK、Mastra 三套是目前活跃的 harness 构建工具包，比 LangChain 更轻、更聚焦 production agent。

团队级部署，Devin、Factory。把 harness 包成 SaaS 给整个工程团队用。

国内场景，Trae（字节）、CodeBuddy（腾讯）、Coze（字节通用 agent 平台）、Manus（端到端通用 agent）。每家底层模型不同，harness 设计哲学不同。选之前先看它们的 harness 怎么处理 context 管理和权限边界这两件事。
