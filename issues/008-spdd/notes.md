# 008 · AI 让你效率翻倍，团队交付却一动没动 · notes

## 定位

这不是「翻译 / 安利 SPDD」的文章，是**报道 + 评判**。SPDD 是 Thoughtworks 2026-04-28 才提出、Fowler 背书的新方法，三周大，后面一定会有一堆中文号翻译它。本文的价值不在翻译，在**评判**——带着数据（Faros）和批评者（Böckeler / Wattenberger）把它放进版图，给读者一个真实的判断，不是 hype。

跟 003（SDD / 岗位塌缩）不是一回事：003 是劳动/角色随笔，008 是一个具体方法论的报道 + 检验。

## 一句话钩子

AI 让你团队里每个人的产出翻了倍，团队交付速度却一动没动——这篇讲瓶颈去哪了，以及一个叫 SPDD 的新方法在赌什么、值不值得跟。

## 核心观点（这篇要让读者改变的认知）

1. **「个人快了、团队没快」不是感觉，是被测量过的。** Faros AI 测一万多名开发者：个人任务 +21%、合并 PR +98%（接近翻倍）、而 DORA 四项交付指标零变化。瓶颈不在生成代码。

2. **瓶颈移位了。** 从「写代码」移到「review + 集成 + 对齐」。AI 代码不是单纯更多，是单位更多 + 单位更难审（CodeRabbit：AI 协作 PR 问题数约 1.7×；评审时长 +91%）。

3. **病根是「聊天室开发」。** 打开对话框随手输一句、复制粘贴、提交。那句 prompt 没版本、没记录、没人能 review、不可复用。换个人重做同样的功能又得重聊。个人快、团队乱，根子在「把 AI 当个人工具，没当成工程流程」。

4. **SPDD 是当下对这个问题最像样的一个答案。** 把 prompt 当代码管：结构化（REASONS Canvas 七维）、版本化、可评审、可复用；现实和 prompt 偏离时先改 prompt 再重新生成代码（prompt 是需求到代码链条上唯一的真相来源）。

5. **但它在赌一件历史上反复失败的事，而且批评者已经在场。** SPDD 只有三周大。Thoughtworks 自己人 Böckeler 质疑 SDD：评审负担反而更重、虚假的控制感、重蹈模型驱动开发覆辙。Augment 的 Wattenberger：唯一能 100% 信任的文档是代码本身，软件史上每次「文档优先」都因同一原因失败。连最靠近这件事的人都没共识。

6. **读者该带走的判断（verdict）。** 诊断是铁的——瓶颈确实移位了，别再用「个人速度」衡量 AI。SPDD 这类「把上游结构化」的方法值得认真看，但它赌的是文档/spec 优先这件历史败绩。值不值得跟取决于场景：长期维护的业务系统、强合规、多人协作要可追溯 → 值得试；hotfix、探索性验证、一次性脚本 → 别上这套。

7. **更深一层（SPDD 原文作者 Zhang / Xia 的话，必须归属）。** AI 时代拼的不是模型 IQ，是工程师的认知带宽。能想清楚问题、建对抽象、划对边界，AI 才帮得上；想不清楚，AI 生成得越多、垃圾越多。结构化只是逼你把「想清楚」变成可复用的工程资产。

## 读者画像

joy-studio 核心盘——工程师、技术负责人、技术 PM、CTO、独立开发者。团队里在用 AI 写代码（Copilot / Cursor / Claude Code），亲身感到「个人快了、项目没快、甚至更乱」。听过 SDD / spec-kit / vibe coding 这些词，不需要从 0 解释。不是完全不写代码的人。

读者最常见的误解：用「个人写得多快」来判断 AI 给团队带来的价值；以为「AI 没让团队变快」是 AI 不行。

## 大致提纲（6 章，章节数可调）

### 01 每个人都快了，团队没动

- 事实开篇，不用钩子腔。Faros：一万多开发者，个人 PR +98%，DORA 四项零变化。
- 立起反差：你以为 AI 让团队快了，数据说没有。
- 这不是 AI 不行，是瓶颈不在你以为的地方。
- 收口：引出全文要回答的两件事——瓶颈去哪了、有没有解。

### 02 瓶颈移到了哪

- 瓶颈从「写代码」移到「review + 集成 + 对齐」。AI 代码单位更多 + 单位更难审（CodeRabbit 1.7×、评审时长 +91%）。
- 病根：「聊天室开发」——随手输一句、复制粘贴、提交。那句 prompt 没版本、没记录、没人 review、不可复用。
- 「把 AI 当个人工具」vs「当工程流程」——个人快、团队乱的真正分界。
- 收口：法拉利开烂泥路当画面——发动机再强，到达时间取决于路况。

### 03 SPDD：把 prompt 当代码管

- SPDD 是什么、谁提的——Thoughtworks（Wei Zhang / Jessie Jie Xia），Fowler 背书；如实说它只有三周大。
- 核心理念：prompt 当可版本化 / 可评审 / 可复用的资产；问题不是「怎么生成更多代码」，是「怎么让 AI 改动可治理」。
- 黄金法则：现实和 prompt 偏离，先改 prompt 再重新生成代码；prompt 是唯一真相来源。
- 计费引擎案例高层带过（细节留给 06 章教程）；99% 标注为「提出方对自身案例的自述」。
- 收口：SPDD 不是孤例——它属于 SDD 大家族（spec-kit / Kiro / Tessl），差异在「上游载体是结构化 prompt 而非独立 spec 文档」。

### 04 但它在赌一件反复失败的事

- 结构性反方 / steelman，不是装点。
- Böckeler（Thoughtworks 同门，同发在 Fowler 站）：一刀切工作流不成立、评审负担反而更重、虚假控制感、重蹈模型驱动开发覆辙。
- Wattenberger（Augment）：唯一能 100% 信任的是代码本身；文档优先历来都失败。正面回答「prompt 凭什么不腐烂」——不会不一样，AI 只让腐烂更贵。
- SDD 在规模下崩（协调开销吃掉个人提效）；vibe coding 之争（结构化牺牲快和流畅）；连支持 SDD 的 arXiv 论文自己都列了 over-specification、spec rot。
- DORA 2024 vs 2025 反转放这里：2024 说拖累、2025 说吞吐转正、但稳定性始终为负。两年都呈现，不许只引有利的一年。

### 05 那到底该不该跟

- verdict。诊断是铁的（瓶颈移位），别再用个人速度衡量 AI。
- SPDD 这类方法：适合什么（长期维护业务系统、强合规、多人协作要可追溯）、不适合什么（hotfix、探索性验证、一次性脚本）。
- 给读者一个判断口诀带走。
- 收口：认知带宽那句（归属 Zhang / Xia）。verdict 不是「快去用 SPDD」，是「不管你用不用它，瓶颈已经移位，你得有个对策」。

### 06 REASONS Canvas 怎么落地（教程）

- 给「读完决定要试」的读者的落地章。
- REASONS 七维度逐个讲清——R 需求 + 完成定义 / E 实体与关系 / A 实现策略 / S 系统结构与影响 / O 操作步骤（细到方法签名）/ N 跨切面规范 / S 安全边界。
- 三组划分：抽象层（R+E+A）/ 执行层（S+O）/ 治理层（N+S）。
- 计费引擎案例完整走一遍（六步：分析文档 → 锁边界 → canvas → 逐步生成 → 测试脚本验证）。
- ⚠️ 教程章放 verdict 之后，作为落地附录；若觉得断气口，可把 REASONS 详解前移并入 03、06 只留案例。这是唯一可调的结构点。
