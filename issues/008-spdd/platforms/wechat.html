AI 让你效率翻倍，团队交付却一动没动

写给在用 AI 写代码的团队

[ 头图 · 在公众号编辑器替换为题图 ]

AI 写代码这一年，最常见的一个错觉，是把「我变快了」当成了「我们变快了」。

它们不是一回事。

中间隔着一道沟，而这一年，AI 在让每个人变快的同时，也把这道沟撑得更宽了。

01

每个人都快了，团队没动

一段 prompt 敲进去，回车。几秒钟，一个昨天还得写一上午的功能，成了。

你往椅背上一靠，心里冒出来那句话是：这东西让我快了 10 倍。

这不是听说的，不是哪条推上看来的。是你自己，坐在那台电脑前，亲手干出来的体感。

但同一段时间里，还有件事，你大概也觉出来了。

自从整个团队都用上 AI 写代码，每个人单独干活确实快了，可整个项目的交付，没快多少。

有时候甚至更乱：代码一下子一大堆，review 的时候看不太懂，bug 也没见少。

个人在飞，项目在原地。

这个反差不是错觉，是被测出来的。2025 年，工程效能平台 Faros AI 调了一万多名开发者、一千多个团队的真实提交记录。

个人这一侧，数字很亮：人均完成的任务多了 21%，合并的 PR 数涨了 98%，接近翻倍。

团队那一侧，Faros 盯的是 DORA 那四项指标：一个改动多久能送到用户面前、出了故障多久能恢复、上线的失败率、部署有多频繁。这四项，才是用户真正能感受到的交付。

它们一项没动。

Faros 自己的总结很干脆：开发者产出的 PR 几乎翻倍，团队交付一动没动。

你体感快了 10 倍。

实测下来，个人快了 1 倍，团队快了 0。

这不是你们团队的特殊毛病。Faros 那份数据覆盖一千多个团队，结论高度一致：个人指标普遍往上抬，团队交付普遍不动。这是结构性的。

也就是说，AI 真真切切地让每个人都快了。可这些多出来的速度，没有一点变成项目的速度。

它在中间某个地方，整段整段地漏掉了。

02

瓶颈移到了哪

写代码，从来不是软件交付里最慢的那一步。

一个功能从想法到上线，要走完想清楚需求、设计、写代码、review、测试、集成、部署一长串。AI 大幅压扁的，只是写代码这一格。其他每一格，它一寸没碰。

更麻烦的是，它把别的格子撑大了。

AI 写得快，代码量就暴涨。Faros 那份数据里，人均 PR 接近翻倍，单个 PR 的平均体积涨到了原来的两倍半。代码多了，下游所有要处理这些代码的环节，工作量跟着涨。Faros 测到的代码评审时长，涨了 91%。

而且 AI 的代码不只是更多，是单位更难审。代码评审工具 CodeRabbit 分析过 470 个开源 PR，AI 参与的 PR 平均每个有 10.83 个问题，纯人类写的是 6.45 个。问题密度差不多 1.7 倍，逻辑错误更多，安全漏洞也更多。

把这两件事合起来：AI 在写代码这一步给你省下的时间，被 review、集成多吃掉的时间，又还回去了。个人那侧涨的 98%，到团队这侧，净值是零。

但代码量暴涨只是表象，底下还有一层。

现在大多数人用 AI 写代码，是这样的：打开一个对话框，敲一句「帮我写一个计费功能」，AI 吐一段代码，你复制、粘贴、改两下、提交。

这种用法可以叫它「聊天室开发」。

聊天室开发有个要命的地方：你输进去的那句话，没有版本、没有记录、不进任何人的视野。它在你的聊天历史里待一会儿，就沉下去了。

后果是，没人能 review 你那句 prompt，能被 review 的，只有它吐出来的代码。下个礼拜换个同事做一个几乎一样的功能，他没法在你的基础上接着干，只能重开一个对话框，从头聊一遍。

每个人的每一次思考，用完即弃，谁也接不住谁的。

个人快、团队不快，根子就在这里。你把 AI 当成了一个个人工具，像一个更快的键盘。个人工具能提升的，只有个人速度。

而团队的交付速度，靠的是一套流程，一套让思考能沉淀、能传递、能复用的流程。聊天室开发把每一次跟 AI 的协作，都锁在了个人那一层，一点没漏到团队那一层。

打个比方。你买了一辆法拉利，开上了一条烂泥路。发动机确实强，但你的到达时间取决于路况，不取决于马力。

AI 是那台发动机，它真的强。但团队交付的路况，是 review、集成、意图对齐，它一寸没修。

所以真正的问题，从来不是怎么让 AI 生成更多代码。是另一个：怎么让 AI 写出来的代码，团队管得住、看得懂、用得上。

03

SPDD：把 prompt 当代码管

2026 年 4 月底，Thoughtworks 的两个人，工程师 Wei Zhang 和 Thoughtworks 全球 CIO Jessie Xia，在 Martin Fowler 的网站上发表了一篇文章，提出一套做法，叫 SPDD，Structured-Prompt-Driven Development，结构化 prompt 驱动开发。Martin Fowler 本人在 X 上转发推荐了它。

先说清楚它有多新。这篇文章发表到现在，三个礼拜。你眼下能搜到的关于 SPDD 的一切，几乎都指回 Fowler 那一篇原文。它不是一个被行业广泛采用的标准，是一个刚冒头、但来路够硬的提案。它出自 Thoughtworks，挂在软件工程领域最有分量的个人网站上。

SPDD 要做的事，一句话能说完：把 prompt 当代码一样管理。

聊天室开发里，prompt 是一次性的，用完即弃。SPDD 要做的，是把 prompt 从聊天记录里捞出来，变成一个正式的工程产物，能进版本库、能被 review、能被下一个人复用、能随项目一起演进。那句飘在聊天历史里的话，就变成了一份留得住、传得下去的东西。

这个想法不只是 SPDD 一家在提。2025 年一篇 arXiv 论文专门指出，跟源代码不一样，prompt 几乎从不被版本化、评审、维护，并主张把 prompt 当成一等公民来对待。一篇跟 SPDD 毫无关系、还更早的论文，指向了同一个方向。

SPDD 里有一条规则，是整套方法的轴心，原文叫它黄金法则：当现实和 prompt 偏离时，先改 prompt，再从 prompt 重新生成代码。

这一步是反直觉的。直接改代码两分钟的事，绕回去改 prompt、再重新生成，明显更慢。

但它决定了意图留不留得住。以前发现 bug 直接改代码，改完能跑了，可你当初为什么这么设计、那段 prompt 原本想表达什么，这个意图随着你直接改代码，悄悄消失了。三个月后另一个人接手，他只看得到代码现在的样子，看不到它为什么是这样。先改 prompt 再生成，意图就一直活在 prompt 里。它成了从需求到代码这条链上，唯一的、始终新鲜的真相来源。

代价也在这里：每一次改动，哪怕很小，都得走一遍改 prompt、重新生成、再验证的全流程。改得越碎，这套流程越重。这是 SPDD 要你先付的税。

Zhang 和 Xia 在原文里点明了 SPDD 冲着什么去：真正的问题不是怎么生成更多代码，是怎么让 AI 生成的改动可治理、可评审、可复用。

SPDD 不是凭空冒出来的，它属于一个更大的家族，叫 spec-driven development，规范驱动开发，简称 SDD。这个家族里声量最大的是 GitHub 官方的 spec-kit，到现在攒了将近十万个 star；还有 AWS 的 Kiro、创业公司 Tessl。它们的共同主张是同一句话：上游那份东西，一份 spec，或者一份 prompt，才是真相来源，代码是它的下游产物，要改先改上游。

SPDD 在这个家族里的特别之处，在上游那份东西的形态。spec-kit 让你写的是一份独立的 spec 文档；SPDD 强调的，是把 prompt 本身结构化。你最终交给 AI 的还是 prompt，只是这个 prompt 不再是随口一句，而是一份有结构、能管理的工程文档。

prompt 怎么个结构化法。SPDD 给的模板，叫 REASONS Canvas，一张有七个维度的表。动手写代码之前，你先把这七格填完。REASONS 是这七个维度的首字母：Requirements、Entities、Approach、Structure、Operations、Norms、Safeguards。

抽象层 · 意图与设计
  R  需求   解决什么问题,做到什么程度算完
  E  实体   涉及哪些业务实体,彼此什么关系
  A  方法   用什么策略来实现

执行层 · 实现路径
  S  结构   改动落在系统哪处,牵动哪些组件
  O  操作   拆成可测的步骤,细到方法签名

治理层 · 通用标准
  N  规范   命名、可观测性、防御式编码
  S  边界   性能红线、安全约束、不变量

图 3 · REASONS Canvas 七个维度 · 写代码前先把意图锁死

七格填完，意图、实现路径、不能碰的边界，全锁死了。AI 拿到的不再是一句模糊的话，是一份边界清楚的合同。

Wei Zhang 还开了一个配套的开源工具 open-spdd，是他的个人仓库，不是 Thoughtworks 官方项目。仓库里有句话点得挺准：普通 AI 生成的计划是建议，REASONS Canvas 是契约。区别在于，契约写明了方法签名、错误处理、执行顺序，AI 没有自由发挥的余地。

SPDD 原文走了一个完整的例子。要给一个 token 计费系统加功能：支持标准、高级两档订阅，还要按 AI 模型差异化定价。按 SPDD 的流程，先生成分析文档锁住业务边界，再填 REASONS Canvas 把实现路径推演一遍，然后 AI 按 Canvas 一步步生成代码，最后用自动生成的测试脚本验证。原文说这次实现的意图对齐度大约 99%。

这个数字要看清楚。它是 SPDD 提出方对自己案例的自述，不是第三方测出来的，意图对齐度也不是什么有统一定义的标准指标。把它当成方法作者觉得这一次跑得很顺，别当成一个被验证过的成绩。

这个例子里有一点真的值得留意：到了 review 这一步，做的事变了。review 一份用 SPDD 生成的代码，你手里有那份 REASONS Canvas，你不是在大海捞针找 bug，而是核对代码有没有忠实实现 Canvas 里钉死的意图。review 从猜作者想干嘛、顺便找错，变成了比对意图和实现。

如果这套真能成立，第二章那个团队瓶颈，那个又慢又难的 review，确实被它正面瞄准了。

04

但它在赌一件反复失败的事

要给 SPDD 泼冷水，最有分量的一个人，来自 Thoughtworks 自己。

Birgitta Böckeler 是 Thoughtworks 在 AI 辅助开发领域很受认可的作者，文章跟 SPDD 发在同一个网站、Martin Fowler 的站上。系统体验过 SDD 这一类工具之后，她的判断里有一记，正打在 SPDD 最不愿意被打的地方。

SPDD 整个卖点，是治 review，让 review 从找 bug 变成比对意图。

Böckeler 实测下来的体感，正好相反。面对一大堆冗长的 markdown 文件，她说了句很重的话：她宁愿 review 代码，也不愿意 review 这一堆 markdown。

把这句话摆在 SPDD 的承诺旁边。SPDD 说它让 review 变好；离它最近、最懂行的同门，实测说 review 变差了。你的 review 对象从代码，变成了代码加一大叠 prompt 文档，总量更多，更乏味。

这不是一个边角问题。这是 SPDD 的核心承诺，和一份一手实测体感，正面打架。

Böckeler 还有两刀。一刀：一刀切的流程不成立，同一套重家伙套到小改动上，纯是负担。另一刀更凉：哪怕你搭了再精致的流程，AI 该忽略指令照样忽略，该误读代码照样误读。Canvas 给你一种全锁死了的安心，可模型并不真的受合同约束。她管这叫虚假的控制感。

她最后点了一段历史。SPDD 这套东西，像在重走 model-driven development（模型驱动开发）的老路。那也是一套画好上游、自动生成代码的承诺，最后换来的是僵化和不可控。

另一个人下手更狠。Amelia Wattenberger，来自 Augment Code。

她的判断是一句话：唯一能 100% 信任的文档，就是代码本身。

SPDD 把 prompt 抬成需求到代码之间唯一的真相来源。Wattenberger 说，这件事软件业试过无数次，每一次都失败，而且都败给同一个原因：它要求开发者持续做一件没人看见、也没人奖励的维护工作。文档优先的尝试，没有一次活下来。

prompt 不会例外。它一样会跟代码慢慢对不上、慢慢腐烂。区别只在于，在 AI 的场景里腐烂的代价更高：一个 agent 会拿着一份已经过时的 prompt，自信地生成代码，而且不会提示你哪里不对。一份过期的 prompt，比一份过期的设计文档更危险。

不只是反对的人这么说。一篇正面研究 SDD 的学术论文，自己就列了 SDD 的毛病：过度规范、规范腐烂，还有虚假的信心，一份正确的 spec 照样可能掩盖一个错误的需求。连支持者都把这些坑写进了论文。

上面这些，是观点和实测体感。还有一个数字。

研究机构 METR 在 2025 年做过一个实验：让一批有经验的开源开发者，在他们自己熟悉的成熟代码库上干活，一半用 AI，一半不用。结果是，用 AI 的那批，完成任务平均慢了 19%。更扎心的是，他们事后还以为自己快了 20%。

这个数字得老实说清楚边界。METR 自己声明，这只是资深开发者加熟悉的成熟代码库这一个特定切片，不代表所有开发场景；而且 METR 在 2026 年初已经部分收回了这个强结论，承认实验设计有偏差、正在重做，新数据甚至可能低估了 AI 的好处。

所以别拿它去证明 AI 让所有人变慢。但它仍然戳破一件事：连资深的人、在自己最熟的代码上、AI 最该帮得上忙的场景，证据都是混的、甚至偏负的。你那个快了 10 倍的体感，本身就比你以为的脆。

还有一层，关于团队规模。十个开发者，每个人都认真跑一遍 SDD 流程，结果往往是代码产出更多了，但冲突、重复、架构漂移也更多，集成时返工更狠。个人的提效，被协调的开销吃掉。于是又回到那个反差：个人快，团队不快。只是这一次，连 SDD 自己都可能是问题的一部分。

最后一组数字，来自软件交付领域最被当回事的年度研究，谷歌的 DORA 报告。2024 年那份的结论很硬：AI 显著提升了个人生产力，但它对团队的交付吞吐和稳定性，都是负面影响。2025 年那份翻了一半：吞吐变成了正相关，团队慢慢学会了怎么用它。但另一半没翻，AI 和交付稳定性之间，到今天还是负相关。

DORA 给的解释值得记下来：AI 不会修好一个团队，它只会放大这个团队本来的样子。强的团队用 AI 变得更强，挣扎的团队用 AI，只会让原来的问题被放得更大。

把这些声音收在一起，能听出一条共同的低音。Böckeler、Wattenberger、那座 model-driven development 的旧坟，他们说的是同一件事：让上游那份东西凌驾于代码之上，这个念头，软件业反复动过，反复失败。

SPDD 赌的是这一次不一样。赌注背后，是一整座坟场。

05

那到底该不该跟

先说铁的那部分。AI 让个人快了、让团队没快，瓶颈从写代码移到了 review、集成、对齐。这个诊断是对的，而且它不依赖 SPDD 成不成立。

它有 Faros 一万多人的数据撑着，有代码量、评审时长、缺陷密度的数字撑着。不管你最后用不用 SPDD，这个认知你都得换上：别再用个人写得多快，来衡量 AI 给团队带来的价值。那个衡量会让你一直高兴，也会让你一直看不见真正的问题。

再说 SPDD 本身。它是不是答案，现在没人能拍胸脯。它三个礼拜大，没有大规模、长周期的真实战绩，连它的同门都在公开质疑它。

更要紧的是，上一章那座坟场是真的。文档优先、上游优先，软件业反复试、反复败。SPDD 赌的是这次不一样：因为 AI 让 prompt 不再是写完没人看的文档，而是真的会被拿去生成代码的东西，维护它第一次有了直接的回报。这个赌注有它的道理。但它仍然只是个赌注，赌的还是那件输过很多次的事。

所以该不该跟，不是 yes 或 no，是看场景。

值得认真试的场景：需要长期维护的业务系统；金融、安全这类强合规、要求全程可追溯的地方；多人协作、交接频繁、意图必须留得住的项目。这些地方，SPDD 那套额外的功夫，买到的是真东西。

不值得上的场景：hotfix，这种时候速度压倒一切，七维 Canvas 是累赘；探索性的技术验证，你自己都还没想清楚要做什么，没有意图可锁；还有写完就扔的一次性脚本。

口诀可以更简单：这段代码，你三个月后还会回来改它吗。会，意图就值得用结构留住；不会，随手聊完就够了。

最后一件事，比方法论更深。这句不是我的原创，是 SPDD 原文作者 Zhang 和 Xia 说的：AI 时代，软件开发不是一场模型 IQ 的比赛，是一场工程师认知带宽的比赛。

模型已经够强了，强到不再是瓶颈。瓶颈是你：你能不能想清楚问题、建立对的抽象、划下合理的边界。想清楚了，AI 能帮你飞快地把它变成代码；没想清楚，AI 会用十倍的速度，把一团模糊放大成十倍的麻烦。

SPDD 这个工具本身能火多久，不重要。重要的是它戳中的那个方向没错：AI 越强，把问题想清楚这件事，就越值钱。

— 完 —
