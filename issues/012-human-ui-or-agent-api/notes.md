# 012 · AI 时代的软件，到底是给人用，还是给 AI 用？ · notes

> 状态：已发布。

## 一句话钩子

过去的软件把能力做成页面、菜单和按钮，因为操作者一直是人；当 AI 开始替人操作软件，产品不能只增加一个聊天框，而要同时提供可组合的机器能力、可信的人类界面和独立于模型的权限边界。

## 核心观点

这篇不只判断 UI 会不会消失，而是提出一套可落地的软件形态：

> **未来的软件不该在“给人用”和“给 AI 用”之间二选一。它需要一个确定性的能力核心，再分别提供给 AI 调用的能力入口和给人判断、确认的控制界面。AI 负责理解意图与编排，人负责目标、选择、授权和例外；真实状态、权限与交易仍由普通软件可靠执行。**

暂定参考架构：

1. **领域能力层**：订单、库存、日历、文档、支付等真实状态与确定性操作。
2. **机器契约层**：面向 AI 的能力发现、结构化输入输出、长任务状态、错误语义与版本协商，可由 MCP、A2A、UCP 等协议承载。
3. **AI 编排层**：理解用户意图，选择并组合能力，不直接保存业务真相。
4. **人类控制面**：稳定工作台 + 按任务生成的表格、地图、表单、预览和审批界面。
5. **安全控制面（贯穿所有层）**：身份、最小权限、预览/提交分离、幂等、限额、审计与回滚。

文章必须回答的不只是“应该长什么样”，还要回答：

- 现有 SaaS 如何逐步改造成这种形态，而不是全部推倒重写。
- 哪些界面适合动态生成，哪些必须保持固定。
- 什么才算真正面向 AI 的 API，不是简单给旧接口套一层 MCP。
- AI 如何发现能力、维护任务状态、处理失败和请求人工确认。
- 人、AI 与软件分别对什么负责。

## 读者画像

产品经理、独立开发者、工程师、设计师与技术负责人。知道 API、Agent、MCP 这些词的大致含义，不需要协议入门；真正关心的是下一代产品该怎么设计、现有系统该从哪里动手。

读者可能有两种先入判断：

- 聊天框会替代所有界面。
- AI 只是现有软件上方多出来的一个输入框，底层不用变化。

本文要同时纠正两边：纯聊天无法承担复杂比较、精细编辑、持续监控和高风险确认；只加聊天框也无法让 AI 获得稳定、可审计、可恢复的操作能力。

## 事实底座（已确认）

- OpenAI Apps SDK 已让第三方应用在对话中提供自然语言入口和交互界面，底层建立在 MCP 上。
- MCP Apps 已在 2026-01-26 成为首个正式 MCP 扩展，工具可返回表单、仪表盘、可视化和多步骤界面，并在沙箱 iframe 中运行。
- A2A 用 Agent Card、任务、消息和产物描述 Agent 之间的发现与长任务协作。
- Google 的 2026 协议指南把 MCP、A2A、UCP、AP2 分别放在工具连接、Agent 协作、交易过程和授权审计位置。
- Anthropic 2026-05 的公开数据称，用户批准约 93% 的权限弹窗；高频逐次确认会产生批准疲劳，硬边界需要沙箱、虚拟机与网络出口控制。

完整来源与诚实边界见 [experiments/research-brief.md](experiments/research-brief.md)。
