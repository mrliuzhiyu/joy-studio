折腾了两年的 AI 记忆系统，最后是一个 markdown 文件

MemGPT、Mem0、Letta、向量数据库、知识图谱——2026 年这些方案的发明者本人，都在退回 markdown。

你跟 ChatGPT 聊到第十轮、它还记得你叫什么、你在做什么项目、上一次卡在哪——这件事，记忆不在模型里。

模型每次对话都是新人。让它「记得你」的，是模型外面那一层程序——业内叫 AI 记忆系统。

过去两年这一层是 GitHub 上最拥挤的赛道之一。

Mem0（54k stars）、Letta、Zep、cognee、Memary、LangMem 一连串记忆框架冒出来。

做 AI 应用的团队挨个评估、数据库选型、上 Postgres + pgvector、搭向量检索、试 RAG、加知识图谱。这两年大家都在卷谁的记忆系统更精致。

2026 年的转折是这样的。

写出最重要的那篇论文（MemGPT）的人自己，公告把整套方案标成「过时」、退回了最朴素的实现：一个文件夹、几个 markdown 笔记、用 grep 搜文字。

用得最广的 Mem0、头部 production AI 编程 agent Claude Code，独立得出了同方向的判断。

这篇文章带你走完三件事：这一层是怎么走到今天的、production 团队现在到底用什么、接下来五年它会去哪。

01

一篇论文被自己人抛弃了

2023 年 10 月、UC Berkeley 三个研究者发了一篇 16 页的论文叫 MemGPT: Towards LLMs as Operating Systems。

论文的核心想法：把大语言模型当成一个操作系统。模型自己一次能装下的内容范围（context window）就是 RAM——快但小。要长期保留的东西放进档案库（archival memory）——慢但大。模型自己决定哪条记忆什么时候在哪一层、像电脑的操作系统管内存一样。

这套范式成了过去两年 AI 记忆赛道的圣经。Mem0、Zep、cognee、Memary、LangMem 这些后来冒出来的记忆框架几乎都从 MemGPT 的思想生长出来。论文一作 Charles Packer 自己开了家公司叫 Letta、拿了 1000 万美元种子轮（Jeff Dean 个人投的）、做的就是这套思想的 production 级实现。

2026 年 2 月 12 日、Letta 在自家博客发了一篇公告叫 Introducing Context Repositories。

新方案：把 AI 的长期记忆改成一个 git 跟踪的 markdown 文件夹、AI 用 grep 和 glob 这种几十年前就有的 Unix 命令来查。按 Letta MemFS 文档自己的说法，目前甚至不支持语义搜索——只用最传统的精确文本匹配。

公告里把 MemGPT 那套三层记忆结构明确标记成 prior approach——之前的方案。

写论文的人、自己把论文拆了。

这件事不是 Letta 一家发生的孤立事件。

Mem0 的 GitHub repo 调研时 54.6k stars，是这两年用得最多的 AI 记忆框架。它在 2026 年 4 月升级了核心算法。

从过去主打的向量检索，变成 hybrid retrieval（混合检索）：把 semantic（语义）、BM25（一种基于词频的传统搜索算法、是搜索引擎在向量出现前几十年用的主流方法）、entity matching（实体匹配、看记忆里有没有出现你问句里提到的具体名字 / 名词）三种信号并行打分融合。

这版升级里有一个细节：graph relationships（图谱关系、Mem0 之前主推的关系存储能力）不再暴露给查询使用，退到后台只作为打分的信号之一。不是去掉了图，是把图退到了信号层，不让查询者直接走图。

Anthropic 给 Claude Code 的官方记忆文档写得清清楚楚：它的记忆系统就是两类 markdown 文件——CLAUDE.md 和 Auto Memory，加 Claude 自己用标准文件工具读取。没有向量数据库、没有图谱、没有 embedding、没有任何「花哨」的检索基础设施。

三家公司——MemGPT 论文的发明者团队、用得最广的开源记忆框架、头部 production AI 编程 agent——都在 2026 年这几个月，用各自的方式说同一件事：

AI 记忆这一层、过去两年走的那条复杂化路径，是过度设计。

02

记忆是装在模型外面的

要理解为什么 markdown 加文本搜索就够，得先把 AI 模型自己是什么讲清楚。

模型自己没记忆——这件事一句话讲完。

你跟 ChatGPT 聊天、它记得你上一句说什么，看上去是在「记得」。但模型本身没有任何状态保存。每次推理对它来说都是全新的，它不知道你上一秒说过什么、不知道你叫什么、不知道现在几点。

ChatGPT 这个应用之所以看起来有记忆，是因为它每次给模型发请求时把过去的对话历史完整附带过去。模型看见的是「过去聊过的全文 + 你这条新话」，它根据这一整段产出回答。看似多轮对话，其实每一次都是单次问答，只不过输入越来越长。

打个比方——模型是一个被关在房间里只会写字的人。这个房间没有窗户、没有电话、没有任何外部连接，也没有「前一秒的记忆」。你递一张纸条进去，纸条上抄满你跟他过去聊过的所有内容、再加上你这次的问题，他写一段回答给你，纸条递回来。仅此而已。

下次你再问，要再递一张新纸条进去——上面又得抄上之前所有的对话内容（包括他上次的回答），加这次的问题。你不抄，他什么都不知道。

这就是 AI 模型的真相。

所谓「AI 记得你」，记的不是模型本身、是模型外面那个程序。它把你过去说过的话按某种方式存下来，在你下次发消息时挑出相关的部分塞进这张「纸条」。这层「挑相关、塞进去」的机制就是记忆系统。

上一期讲 harness 时，把这套「外面的程序」叫做模型外面那一层执行壳。记忆系统是这层壳里专门管「记什么 / 取什么 / 塞回 prompt」的那一块。

AI 记忆的设计问题、本质上不是设计模型——是设计这层壳里的笔记本机制。

而 Letta、Mem0、Anthropic 这三家在 2026 年告诉行业的是：这个笔记本不需要做得太花哨。

顺便澄清一个常见混淆——记忆系统跟 RAG（Retrieval-Augmented Generation，检索增强生成）是有重叠但不是一回事。

RAG 是更宽的概念：任何「先检索一些文档、再丢给模型生成」的模式都算 RAG。记忆系统是 RAG 的一种特例——检索的对象是「你过去说过的话 / AI 过去帮你做过的事」这种 session-bound（跟用户 / 工作流绑定的）内容。

下面所有讲「记忆系统」的地方都是这个意思，不是泛指 RAG。

03

一篇论文怎么火成行业标准

时间倒回 2023 年 10 月 12 日。

UC Berkeley Sky Lab 给 arxiv 提交了一篇论文。

Sky Lab 是 AI 系统方向最有名的实验室之一，Ion Stoica 是大数据时代 Spark（一个在数据工程领域几乎人人用的开源框架）的创造者之一，是 Databricks 公司的联合创始人。能写进这个实验室的论文，本身就有学术地位的背书。

那篇论文的几位作者——Charles Packer、Sarah Wooders、Kevin Lin、Vivian Fang、Shishir G. Patil、Ion Stoica、Joseph E. Gonzalez。Packer 和 Wooders 是 PhD 学生，Stoica 和 Gonzalez 是导师。

论文标题：MemGPT: Towards LLMs as Operating Systems。

https://arxiv.org/abs/2310.08560

图 3.1 · MemGPT: Towards LLMs as Operating Systems · arxiv:2310.08560

副标题里这个 OS（操作系统）类比，是这篇论文的核心想法。

操作系统是你电脑里那个最底层的程序，Windows、macOS、Linux 这些。它做的关键事之一是管理你电脑的内存层级：内存条（小但快）、硬盘（大但慢）、CPU 缓存（最快但最小）。操作系统帮你自动决定数据放在哪一层、什么时候从慢的搬到快的、什么时候从快的退回慢的。这套机制叫虚拟内存管理，是操作系统几十年发展的核心成就之一。

MemGPT 论文做的事是：把这套虚拟内存的思路搬到 AI 记忆上。

想象一个图书馆。最贵重、最常用的几本书放在图书管理员桌上、伸手就能拿到——是内存。借出去过、可能会再借的、放在借阅区开放书架上——是缓存。冷门、古旧的、放在地下三层档案库里、要专门走流程才能调出来——是档案库。

读者每次来借书，图书管理员要能在三个地方间灵活调度——书一旦从档案库被频繁请求，就要预先调到开放书架上；某本桌上的书三个月没被碰，就放回开放书架。

MemGPT 给 AI 记忆设计了类似的三层：

核心记忆（core memory）：AI 跟你对话时、跟前文一起常驻在它的「视线范围」（context window，就是模型每次能看到的那段文字的上限）里，像图书管理员桌上的书。

回忆记忆（recall memory）：可以搜索的过去对话历史，像借阅区开放书架。

档案记忆（archival memory）：长期冷存储，像地下档案库，等到 AI 需要时再调出来。

最关键的——这三层的搬运、由 AI agent 自己决定。它通过调用工具（tool call，就是模型生成一段标准格式的指令、外部程序去执行）告诉外部程序「把这条从档案搬到核心」或者「这条核心的可以归档了」。AI 自己当自己的图书管理员。

这个想法当年发表时被视为一个浪漫的研究愿景。它把 AI 系统设计的方向，从「让模型记得更多」改成了「让模型自己管理记忆」。论文很快成为 AI 记忆这条研究线的开山作之一。

2024 年 9 月 23 日、一年后，Charles Packer 和 Sarah Wooders 把 MemGPT 商业化、成立 Letta、出 stealth、$10M 种子轮、Felicis 领投、Jeff Dean 个人投资。Letta 当时的产品定位写得很清楚——为 AI agent 提供「stateful（有状态）记忆」的基础设施，把 MemGPT 论文的思想做成开发者用的 SDK（一套代码工具包，让别的开发者能在自己的应用里直接调用）和服务。

同一时间段，整个行业开始卷 AI 记忆框架。

Mem0：把 MemGPT 思想简化成轻量 API 层，把记忆能力作为外挂、加进任何 AI 应用。

Zep：走知识图谱派，强调记忆里实体之间的关系存储。

cognee：走 ontology（本体论）+ 知识图谱，给企业知识库做长期记忆。

Memary、LangMem、Supermemory、MemPalace——一个又一个围绕「让 AI 能跨 session 记得东西」的项目从 GitHub 上冒出来。

每家都在卷：谁的检索算法更好、谁的存储后端更高效、谁的抽象层更优雅、谁的 LongMemEval（500 题长对话评测）跑分更高。

到 2025 年底，AI 记忆框架变成 GitHub 上最拥挤的赛道之一。

MemGPT 那个 OS 隐喻很漂亮。它让 AI 记忆这件事看起来像有标准答案的工程题，所有人都在比谁更精致。

把这三年放在一张时间轴上——

2023-10      ┃  MemGPT 论文 · UC Berkeley Sky Lab · 三层记忆 OS 范式
2024-09      ┃  Letta 出 stealth · $10M 种子 · 论文产品化
2024-2025    ┃  框架爆发：Mem0 / Zep / cognee / Memary / LangMem
2025 年底    ┃  AI 记忆变成 GitHub 最拥挤赛道之一
2026-02      ┃  Mem0 graph 关系退到后台信号层（不再暴露给查询）
2026-02-12   ┃  Letta 公告 Context Repositories · 把 MemGPT 标 prior approach
2026-03      ┃  Claude Code 源码 leak · 印证 markdown + grep 路线
2026-04      ┃  Mem0 hybrid retrieval（向量 + BM25 + 实体）出 v2

从一篇论文统治三年到自我拆台，行业用了 28 个月。

04

Letta 是怎么自己拆台的

回到 2026 年 2 月 12 日 Letta 那篇 Context Repositories 公告。

这次它讲的不是「我们升级了 MemGPT 的检索算法」、不是「我们加了新的存储后端」、不是「我们又在 LongMemEval 上拿了几分」。它讲的是，整套架构换了。

新方案的核心是这样：

每个 agent 都有一个本地的 memory 文件夹，就在你硬盘上的某个目录，文件夹里全是 markdown 文件，每个文件用 YAML frontmatter（一种在 markdown 文件最顶部用结构化数据描述这个文件元信息的格式）说明这个文件存的是什么。

整个文件夹用 git 做版本控制。每次 agent 改了某个文件，必须自己 commit + push（commit 是 git 里「保存这一版」的动作、push 是「把这版同步到中央仓库」），改动才会被「记住」。如果 agent 改错了，回滚到前一个版本就行，这是 git 几十年前就解决的事。

agent 操作记忆的方式是直接用 bash（命令行）操作这些文件。要找东西用 grep（一种纯文本搜索工具、是 Unix 几十年前就有的最朴素搜索方式）、用 glob（按文件名模式匹配的搜索）。要改东西用 sed（命令行文本编辑工具），或者直接读完整个文件再写回去。

图 4.1 · Letta MemFS（memory filesystem）· 只支持 grep / glob，无语义搜索

按 Letta MemFS 官方文档自己的说法：目前只支持精确匹配搜索（grep、glob），没有任何基于语义或 embedding 的搜索能力。

embedding 是上一段讲到的「向量检索」——把文字压成一组数字，按数字距离判断意思相近，是过去两年所有主流 AI 记忆框架（包括 Letta 自己的旧版）的核心。

Letta 公开宣布——它的新一代记忆系统、不要这个能力。

为什么呢？不是技术上做不到。Letta 在公告里给出的解释，加上 production agent（指实际给真实用户跑起来的 AI 程序，对应「实验室 / 演示」的反义）这一年的实践，指向一组共同观察。

MemGPT 的 OS 类比当年很漂亮，但实际跑起来，agent 通过 tool call 调度三层记忆这件事，不是它的强项。模型擅长读文本、不擅长扮演图书管理员。把记忆做成它能直接 grep 的一个文件夹，它自己会用，不用专门学一套 memory API。

AI 写记忆这件事最大的风险是它写错。比如把「这个项目用 Python 3.12」错记成「Python 3.10」，过几天才被发现。MemGPT 那套方案需要专门设计自我修正机制。

git 解决这事的方式简单粗暴：回滚到上一个版本就好。commit history 天然就是审计日志。

production agent 又天然就在用 bash：读文件、跑命令、写文件、看 diff 这些都是它本职。把记忆做成它已经会的工具能操作的，比给它一套新 memory API 更顺手。

把这些放在一起看。MemGPT 那套虚拟内存抽象，在 production 环境里是不必要的中间层。它解决的问题——context 装不下——可以用更简单的方案解决：直接用文件，让 agent 自己读。它制造的复杂度——学一套 memory API、信任 AI 当图书管理员——不值得。

顺带补一笔。Letta 的新方案不只是"退回 markdown"。

Context Repositories 同时引入了一个叫 sleep-time compute（睡眠时计算） 的新机制：多个 subagent 异步操作记忆文件、各自 commit、最后用 git 合并冲突。

这等于把 MemGPT 那种"agent 一边对话一边管记忆"的串行模式，拆成了并发模式。

所以严格说，Letta 是「退回朴素存储 + 换上更现代的并发协调」，不是单纯撤退。

这点细节后面五年值得关注，下一波 agent 记忆架构很可能从这里长出来。

抛弃 MemGPT 这件事由 MemGPT 团队自己做出来，跟外部批评不是一个量级的信号。

外部批评说「这个方向有问题」可以反驳。但当方案的发明者自己用自家的钱、自家的工程时间、自家两年的产品迁移代价，来证明「这条路 production 跑不通」，那是任何 review paper 都给不出的强证据。

05

Anthropic 给的一手答案

跟 Letta 自己拆台同步发生的另一件事——Anthropic 把头部 production AI 编程 agent 怎么做记忆，写在了官方文档里。

Anthropic 的 Claude Code 官方记忆文档写得清清楚楚：它的记忆系统就是两套机制。

第一套 · CLAUDE.md 文件：你（用户）写的、给 Claude 的持久指令。可以放在你项目根目录（./CLAUDE.md），可以放在你用户目录（~/.claude/CLAUDE.md），可以放在系统级目录给整个组织共享，可以放在 ./CLAUDE.local.md 给本地开发用（不进 git）。

第二套 · Auto Memory：Claude 自己写的、基于跟你工作过程中识别出的有用信息（build 命令、API 路径、debug 经验等）。存在 ~/.claude/projects/<project>/memory/ 这个目录，是一个 markdown 文件夹，里面有一份 MEMORY.md（索引）+ 若干主题文件（debugging.md、api-conventions.md 等）。

加载方式按官方文档原话：MEMORY.md 的前 200 行，或前 25KB（看哪个先到），在每次对话开始时加载。

主题文件不预先加载——Claude 在工作过程中如果需要，用它的标准文件工具（read_file 这种）按需读取。

整个机制里，没有向量数据库、没有图谱、没有 embedding、没有任何专门为「AI 记忆」设计的基础设施。就是 markdown 文件加 Claude 自己的标准文件读取工具。

把 MemGPT 范式跟 Claude Code 实际方案画在一起对比——

MemGPT 范式（2023 论文方案）        Claude Code 实际方案（2026）
─────────────────────────           ────────────────────────────
core memory                  ←→     CLAUDE.md
  常驻 context window                 用户写的持久指令 · 启动一定加载

recall memory                ←→     MEMORY.md（前 200 行 / 25KB）
  可搜索的对话历史                    AI 自己写的索引 · 启动加载

archival memory              ←→     主题 markdown 文件
  长期冷存储 + tool call 调度          按需 grep / read_file · 不预加载

模型自己当图书管理员                 标准 file 工具读取 · 无 memory API
（self-managed via tool calls）     （no memory abstraction layer）

左边是浪漫的研究愿景。右边是产品团队三年实践收敛出来的真实形态。

我去 verify 这套设计的具体实现时，走了两条路。

一条是顺着 Anthropic 官方文档读。MEMORY.md 的 200 行 / 25KB 阈值、主题文件按需读、用 Claude 的标准 file 工具，这些参数 docs 里都写得明明白白。一套真的简单的东西，文档里直接讲完，不用藏。

另一条是 2026-03 社区那次源码 leak 之后的分析。Akita on Rails 那篇文章给的几个关键判断：MEMORY.md 是只放 pointers 不放数据的索引、主题文件用 lexical search 拉、autoDream 子系统是 grep 跑 JSONL 日志，跟官方文档说法一一对应。没有「文档说一套、代码做一套」的落差。

这件事跟我之前研究开源记忆框架时的体验形成对照。Mem0、Letta、Zep 这一类，你要理解它们做了什么，得读 SDK 源码、得看 abstract base class 的层层继承、得追 retrieval pipeline 的每一步。Claude Code 反过来：文档读完，机制也基本就这样，没有藏在深处的玄机。

研究完一圈，最大的反差感是这个。

AI 记忆这件事，production 团队最后选的方案不只是「简单」。

是简单到让研究者不敢相信，简单到我自己读完官方文档第一反应是「不会就这吧？」

然后回去看自己用 Postgres + pgvector 折腾出来的那一套，越看越觉得多余。

跟 Auto Memory 配套的，还有一个 Anthropic 自己没正式公告、但社区扒到的功能——社区起名叫 Auto Dream（自动做梦）。

⚠️ 这个名字是社区起的，Anthropic 官方文档里没有；它目前在 Claude Code 的 /memory 菜单里可见，但用 server-side feature flag（服务端的功能开关、可以让一部分用户先用上某功能）控制，还没对一般用户开放。

它做的事是后台主动整理 memory 文件，分四个阶段：

Orient · 定位：扫描已有的 memory 文件，给自己梳理一遍存了什么。

Analyze · 分析：翻 session 转录，找其中高价值的 pattern。

Consolidate · 整合：把新发现的合并进现有的主题文件、做关键维护——相对日期变绝对日期、删掉被新事实推翻的、移除过期、合并重叠条目。

Prune & Index · 修剪和编排：把 MEMORY.md 控制在 200 行以下（这是 Claude Code 启动时实际加载的阈值，超过的部分根本不会读）。

整个机制类比的是 REM 睡眠的记忆巩固：人睡觉做梦时大脑也在做类似的事，把一天的经验整理、淘汰不重要的、合并相关的。

按 Akita on Rails 那篇 2026-04-06 的深度分析转述（这是二手转述），根据 2026-03 Claude Code 源码 leak（Anthropic 不小心发布了一个 npm 包版本，暴露了大约 51 万行 TypeScript 内部代码）推断，Auto Dream 这个子系统的实现就是 grep 搜 JSONL（一种结构化文本日志格式，每行一条 JSON）日志，纯文本操作，没用什么 fancy 的算法。

放在一起看。Claude Code 这套头部编程 agent，记忆系统是 markdown + 标准文件读取。Auto Dream 这个主动遗忘机制，底层是 grep on text logs。

Letta 自己拆掉的，是「AI 记忆需要一套专门设计的虚拟内存抽象」这个假设。Anthropic 是另一家头部 production 团队，从自己的产品经验出发，独立得出了同方向的判断：做记忆系统不需要「专门设计的虚拟内存抽象」。

两家不同方向走来，各自的实践指向同一件事：之前那些更复杂的方案是过度设计。

06

Mem0 的妥协是退潮的预告

Mem0 是这两年用得最多的 AI 记忆框架。Mem0 GitHub repo 调研时 54.6k stars（写时复核），是 Y Combinator S24 的项目，走的是「轻量 API、嫁接到任何 AI 应用」的路线。

Mem0 跟 MemGPT 不是一回事。Mem0 不是 MemGPT 论文一作的公司（那家是 Letta）。Mem0 是受 MemGPT 思想启发的另一派，不是「发明者」、也不是「直接产品化」。它代表的是另一类：基于 MemGPT 范式做出来的下一代框架。

Mem0 的初代设计——以向量检索为核心。

向量检索是过去两年最热的检索方式：把每段记忆压成一组几百到几千维的数字（向量），按距离判断「意思相不相近」，距离近的就召回。它的优势是能处理「用户问的『咖啡』跟记忆里的『拿铁』其实是同一类」这种语义相关性，比纯文本匹配灵活。

2026 年 4 月，Mem0 升级了它的核心算法。按官方说法，新版是 hybrid retrieval（混合检索）：semantic（语义）+ BM25（基于词频的传统搜索）+ entity matching（实体匹配）三种信号并行打分、融合输出。

LongMemEval 上 Mem0 拿到 93.4 分，对比上一版 67.8 分——提升 25.6 分。LoCoMo（另一个长对话评测）拿到 91.6 分，提升 20.2 分。这是 AI 记忆赛道近两年最快进步的一段时间。

但这版升级里有一个细节，值得注意。

按 Mem0 graph memory 文档自己的说法，文档里关于这个变更有两点关键事实：旧版搜索结果里的 relations 字段不再返回数据；entity relationships are consumed indirectly through retrieval ranking, not exposed as a queryable graph structure。

中文意思是：实体关系不再以可查询的图结构暴露，而是间接通过检索打分被消费。

也就是说，Mem0 的「图谱」在新版里不是给查询者直接走的图，而是退到后台当作打分时的一个信号源。

不是去掉了图、是把图退到了信号层。

Mem0 这次妥协是这一波框架退潮的预告。比 Letta 那则公告早 2 个月，可以当预演看。

这件事拆开看是三层：向量这条路独走不通、纯图也走不通、最后只能 hybrid 三种信号融合——但 hybrid 也不是"加更多功能"，是"加更多 + 把不可信的那部分藏到后台"。

向量这条路独走不通：长 context（直接把所有记忆塞进 prompt）+ BM25（传统词匹配）在事实召回上经常赢过纯向量。

向量在 production 还有几个具体痛点。

切段切坏了，把定义和用法分两边：chunking 是按字符数或段落机械切的，定义在第 8 行、用法在第 12 行，搜的时候只命中一边。

ranking 给的"近邻"经常意思相近但答非所问：你问"咖啡机怎么修"，它返回"拿铁配方"。都跟咖啡相关，但不是你要的。

模型一升级，旧 embedding 跟新模型对不上号：要重新 embed 整个库。成本不小，几十万条记忆重 embed 是几小时加几百美金的事。

这些都是"理论上能跑、production 维护起来扎手"的细节。

纯图也走不通：从对话流里抽实体和关系（NER + Relation Extraction，自然语言处理里的两个经典任务）这一步本身准确率不高，抽错的关系会污染整个图。按 HotpotQA 多跳问答 leaderboard 上 2024-2025 的成绩，连最强的模型在多跳实体抽取上也只能做到 ~85% F1（一种衡量准确率的综合指标，范围 0-100），剩下 ~15% 是抽错的。

最后变成 hybrid 这种「三种信号融合」，是工程妥协的体面收尾。

向量对关系无能，最干脆的例子是这个，也是行业里讲解多跳推理（multi-hop reasoning，要在多个事实之间转两次或更多次才能答出来的问题）的标准例子。

你的记忆库里存了两条：

「张三认识李四」

「李四在 C 公司」

你问 AI：「张三跟哪家公司有关系？」

向量检索是这样工作的：把「张三」压成一组数字，把所有记忆条目也压成数字，按距离排序找最近的几条。问题是「张三」在向量空间里跟「李四在 C 公司」这条距离根本不近，因为这条文本里压根没出现「张三」，向量层面就跟「张三」不像。「张三认识李四」这条会被找出来，但只用这一条 AI 回答不出问题，它不知道李四在哪家公司。

知识图谱是这样工作的：张三是一个节点、李四是一个节点、C 公司是一个节点。「认识」是张三到李四的连线，「任职于」是李四到 C 公司的连线。问「张三跟哪家公司有关」——从张三这个节点出发，沿「认识」走到李四，再沿「任职于」走到 C 公司，答案直接就到。

向量擅长找「意思相近的内容」。图谱擅长追「实体之间的关系链」。

需求层面就不是同一类。但图谱建图本身有 ~15% 错误率：抽错了「李四在 C 公司」记成「李四在 D 公司」，查询时图谱给你的答案就是 D 公司，错得理直气壮、还看不出来错在哪。

Akita on Rails 那篇 2026-04 的文章给的最干脆的判断是这样：BM25 没找到，你知道为什么（这个词不在记忆里）。向量库返回错的，你看不出哪里错（拿到的是「看上去合理但实际是错的」那种内容，连诊断信号都没有）。

可解释性是 BM25 派的核心优势：失败你看得见。这件事在 production 比「召回率高几个点」重要得多。

Mem0 把图退到信号层，不是技术问题，是产品判断。它承认了一件事：一个直接暴露给查询的图，对用户来说不好用（错的看不出来）、对开发者来说不好维护（建图错了影响所有查询）。把它退到后台当信号，是把不可信的能力转成辅助打分，工程妥协的体面方式。

07

这一层为什么退回

把三件事并排放：

Letta 抛弃 MemGPT 退回 git markdown。

Mem0 把图退到后台信号层，不再暴露给查询。

Anthropic 一手文档显示 Claude Code 用纯 markdown + 标准文件工具。

三件事指向同一个方向——AI 记忆这一层、正在退回最朴素的「文件 + 文本搜索」。

为什么——三层原因。

第一：长 context 的反扑。

Claude Sonnet / Opus 1M token 上下文已 GA（GA = General Availability，正式对所有用户开放）、Gemini 2.5 Pro 2M token、GPT-5.4 400K token——过去两年最大的模型升级之一，是 context window（每次推理能看到的文字量上限，token 是 AI 模型的处理单位，可以粗略当成「半个汉字」或「一个英文音节」）从 4K-32K 涨到几百万。

原本属于「记忆框架」该解决的核心问题（「context 装不下，所以要外面有个智能记忆系统」）被模型本身吃掉一大半。直接把所有相关记忆塞进 prompt，跟搞一套精致的检索系统比，在事实召回上经常前者赢。

这件事改写了「AI 记忆」这个问题的难度：从「设计一个能压缩 + 检索的智能记忆系统」，退化成「设计一个把对的文件交给模型的简单方案」。

但长 context 不是免费的。按 Akita on Rails 那篇给的数据，200K tokens 一次推理 Claude Sonnet 4.6 收 $0.63，有缓存的 follow-up 降到 $0.10，比一次纯向量检索贵几十到几百倍。延迟也成数量级增加。所以长 context 不是把所有问题都吞掉，是吞掉了「context 装不下」这个特定的痛点；成本和延迟敏感的场景仍然有 RAG / 记忆这类辅助检索的位置。

Akita 那篇文章的精准判断不是 "RAG 死了"，而是更微妙。

RAG 没死，是 retrieval（检索）这一步变笨变便宜了。

2023 年是「弱 reader + 强 retriever」：模型读不动，所以需要精致的 RAG 把最相关的几段挑出来塞给它。

2026 年反过来变成「强 reader + 笨 retriever」：模型能直接读 100 万 token，retriever 用 grep 这种笨办法就够。

模型读的能力涨了 10 倍，retrieval 反而该退到 grep 这种笨办法。

精致的检索逻辑现在解决的是已经被模型自己吞掉的问题。

第二：模型自己读 markdown 比走抽象层快。

一旦 agent 能直接 grep / glob / 读 markdown，为它专门做的 memory API 就成中间层。增加学习成本、增加调试成本、增加抽象漏洞，不增加能力。

Letta 抛弃 MemGPT 抽象、Anthropic 不给 Claude Code 加任何 memory 抽象，都是这个判断。

第三：production 团队都在自建。

Anthropic、Cursor、Letta、Mem0——头部跑 production AI agent 的团队，记忆系统都是自家做的；Letta 和 Mem0 自家也是产品级别的自建实现（它们自己就是 framework，但产品里用的不是别家的 framework）。

LangChain 在 2025 那篇「Your harness, your memory」里把 harness 跟 memory 绑在一起讨论，判断也是同方向：记忆没有跨产品的通用方案。

framework 给的是通用解，production 要的是具体解。每家产品的记忆都是「具体」问题——为这个产品场景、为这种用户、为这类工作流，通用框架在 production 永远会差一截。

把三层原因加起来：AI 记忆框架这一层退回的不是「方向错了」，是「市场不在那」。复杂的检索算法 + 漂亮的抽象 + 跨模态的统一 API——这些是给「通用框架」准备的能力。

但 production 不要通用——production 要具体。

把这件事拉到更高一层看，三家退潮指向的不是"框架做错了"，是整个范式底下的工程压力换了一头——

2023               2026
─────              ─────
弱 reader          强 reader（1M-2M token + reasoning ↑）
（要省 context）   （能直接读全文）
       +                 +
强 retriever       笨 retriever
（精致 RAG          （grep + glob + markdown）
+ vector + chunk）

⇩                  ⇩

工程花在做检索       工程花在 context 工程
（chunking / RAG /  （什么留 / 什么扔 /
 graph / embedding） 怎么排序）

记忆框架退潮的本质，是"哪一头的工程压力被吞掉了"换了。

模型读的能力涨了 10 倍，retrieval 这一头自然该退到笨办法。

那 production 团队现在到底用什么？按场景分，5 类记忆方案的横向对比是这样——

场景               方案                给谁         代表
──────             ────                ────         ────
单用户 / 本地      markdown + 文件搜索 个人开发    Claude Code 风格

多用户 / 权限      数据库 + 向量审计   SaaS 团队   Mem0 / 自建 pgvector

agent 自管理       git + markdown 回滚 垂直 agent  Letta MemFS

知识图谱重度       图数据库 + NER      企业知识库   Zep / cognee

超大规模           全自研              头部厂商    Anthropic / Cursor / OpenAI

挑哪一档要先想清楚两件事：这个 agent 服务多少人 + 失败可见性是不是核心需求。

单用户 / 本地 / 单设备 agent：直接 markdown + 文件搜索。参考 Claude Code 的设计——一份 CLAUDE.md（你写的）+ 一份 MEMORY.md（让 AI 自己写的、限制在 200 行内）+ 几个主题 markdown 文件。Postgres + pgvector 是过度设计。

多用户、需要权限和审计：必须上数据库 + 权限模型。Mem0 比裸搭快，但用之前确认你的需求对得上 Mem0 的能力——hybrid retrieval 对事实召回够，复杂关系查询要单独看。

agent 自管理 + 跨 session 学习：Letta MemFS（git-tracked markdown）这条路适合。git 版本控制天然解决 AI 写错记忆的回滚问题。

知识图谱重度（企业内部知识库、关系链查询是主诉求）：图数据库 + 实体抽取这条仍有位置。Zep、cognee 是这一档活跃的方案。但要做好「建图准确率 ~85%」的预期管理——剩下 15% 是抽错的关系，会污染下游查询。

超大规模 + 跨多团队：必须自建。开源框架在这个体量都会撞瓶颈。Anthropic Managed Agents、Cursor、ChatGPT 这一档全是自研。

看完三家退潮 + 现在选什么，最后一个问题：这一层接下来五年会去哪？四个观察。

长 context 会再扩一个数量级。1M token 已经 GA、2M token 站稳、5M-10M 在路上。当一次推理能装下你两年的对话历史，「记忆框架」这个词本身可能消失，演化成 context engineering——不再是「我怎么把过去检索出来塞进 prompt」，是「哪些东西留在 context 里、怎么排顺序」。Anthropic 那篇 context engineering 长文已经在用这个新框架谈问题。

跨 agent memory protocol 会出现。

现在每家 harness 的记忆互不通：你在 Cursor 教 AI 的 React 偏好，搬到 Claude Code 它不认识。

MCP（Model Context Protocol，Anthropic 牵头的 agent 工具协议）在 tool 层做了协议：Cursor 用某个 MCP server，Claude Code 也能用同一个，工具是跨 harness 的。

memory 层目前还没这种协议，但迟早会有。

先做出来的会拿到一波平台权力，类似 MCP 之于 tool 调用、OAuth 之于身份认证、或者更早 USB 之于硬件接口。

这事会重新洗牌。做底层模型的厂商（Anthropic / OpenAI / Google）和做 harness 的厂商（Cursor / Devin），谁定义这个协议谁拿到下一波平台位置。

多模态记忆刚起步。

现在所有方案都是文字记忆。

你跟 Notion AI 上传一张架构图、一段会议录音、一个 Figma 截图，AI 当下能"看"。但下次对话再问"上次那张图里 Auth 那块用什么数据库"，它不记得。

图、视频、音频、代码截图怎么 index、怎么搜、怎么跟文字记忆混合查询，所有家都还在试，没共识。

这块大概率是下一个「2023 年的 MemGPT 时刻」：会有一篇论文先提出范式，然后被一连串框架追赶，几年后再被 production 简化。

如果你在做多模态 AI 应用，这是接下来 12-24 个月最值得押注的一个方向。

隐私和数据所有权会被强制。你给 AI 喂的记忆——项目代码、工作流、个人偏好——归谁、能不能导出、删除请求多久内必须清干净。欧盟 AI Act 2026 年开始执行，production 团队会被迫提供 memory export / delete 接口。这件事会反过来塑造架构选型——本地 markdown 文件夹比远程数据库在合规上有天然优势。

回到 2026 年 2 月 12 日 Letta 那个公告。

那一天 Letta 在公告里只用「prior approach」四个字，给过去两年所有押注 AI 记忆框架的赌局判了死刑。

下次有人推销一套 AI 记忆方案给你、不管是开源框架还是 SaaS——先问三个问题：

它解决的痛、是不是 context 装不下？如果是、长 context 已经吞掉一大半，先估算一下你的实际 context 需求是不是真的超出 1M token。

它的失败模式可见吗？BM25 找不到、你知道为什么（这个词不在记忆里）；向量返回错的、你看不出哪儿错（拿到的是看上去合理但实际不对的内容）。production 容不下"看不出哪儿错"这种系统。

production 团队真的在这样用吗？还是只是 demo 跑得漂亮、上线后没人维护？看 GitHub stars 没用、看 Anthropic / Cursor / Devin 这些自己跑 production 的团队怎么用才有意义。

这一层的工程教训很简单。它的发明者已经告诉你，答案不在他们一开始的方案里。
