你写的 Agent Harness，正在变成你的技术债

写给正在做 AI agent 的人

[ 头图 · 在公众号编辑器替换为题图 · 可用 cover.html 导出的封面，或另选一张图 ]

过去一年你在做 AI agent，大概写过不少这样的代码：系统提示、工具调用的封装、记忆模块、规划器、多 agent 的编排。

这些代码里有很大一部分，是为今天这一代模型的短板量身写的。

模型补上短板，它们就开始作废。

它们值不值得写不是问题。

问题是写的时候你当它是什么——一笔会一直增值的资产，还是一笔到期要还的债。

01

一个被删掉的架构

2024 年末，LangChain 的工程师 Lance Martin 发布了一个开源的深度研究工具，叫 Open Deep Research。

它的做法在当时很标准：一个大模型负责调度，把用户的研究请求拆成若干报告章节，再交给一组子模型并行去查、各写各的，最后汇总成一份完整报告。

这种一个调度、一组并行执行的结构，业内叫 orchestrator-worker。

Lance Martin 没有让模型自己一边想一边调工具——那时候不敢。

他后来在一篇复盘里写得很直白：2023 年他被 agent 折磨得够呛，模型调工具不可靠，上下文窗口又小。

把流程拆成固定的章节、固定的并行子模型，是为了绕开模型当时靠不住的那些地方。

这一整套硬编码的工作流，本质上是给模型架的一圈拐杖。

一年后，拐杖开始硌脚。

到 2025 年冬天，模型变了。

工具调用变可靠，MCP 这类工具协议起势，agent 被证明很适合做研究这类活。

Lance Martin 发现，他那套精心设计的并行架构成了报告质量的瓶颈。

并行写章节的子模型互相不通气，各写各的，拼出来前言不搭后语——他自己的用词是 disjoint。

他把整套并行写作的架构删了。

改成让一个 agent 自己规划研究、把材料收齐后留到最后一次性写完。

评测分数不降反升。

Lance Martin 删掉的不是 bug。

那套调度逻辑、那些并行的子模型、那套拼装逻辑，在 2024 年每一块都解决了一个真问题，是当时完全正确的设计。

它们过时，不是因为写错了，是因为模型把它们原本要补的洞，自己补上了。

模型外面这一圈东西——编排代码、系统提示、工具调用的封装、记忆、规划循环——这两年业内统一管它叫 harness。

Lance Martin 删掉的，是他那个工具的 harness 里的一大块。

这不是他一个人撞上的事。

browser-use 团队 2026 年 4 月写过一篇复盘，讲他们怎么把一套很重的浏览器自动化 harness 一路删到只剩几百行。

更早，Cognition 的联合创始人 Walden Yan 写过《Don't Build Multi-Agents》，从原理上说清楚了 Lance Martin 撞的那堵墙——并行的 agent 各掌握任务的一个碎片，各自做的判断拼到一起就是冲突。

同一个动作，不同的人在不同的场景里各做了一遍：发现一块 harness 过期了，删掉它。

你这一年写的 harness 代码，大半也会这样结束。

用会计的说法：这部分 harness 不是资产，是一笔按模型发布周期折旧的开支。

你今天写下它，它就开始贬值。

没及时删掉的部分，最后变成技术债——你得花工程时间绕开它、维护它、跟它打架。

这不是说你不该写 harness。

Lance Martin 那套并行架构在 2024 年是必要的，没有它他根本发不出能用的产品。

问题不在写，在于把写下来的每一块都默认成会一直增值的核心资产——不断加层、精心维护、舍不得删。

一块 harness 真正的成本，不在你写它花了多久，在模型让它过期那天，你要花多久才能把它弄走。

02

每一层结构都在补一个洞

Lance Martin 删掉的那套并行架构，往回倒推，每一块都对得上模型在某个时间点的一个具体短板。

这不是他那个工具的特殊情况，过去三年冒出来的 harness 组件，差不多都是这么长出来的。

把时间线拉开：

2023   洞 · 上下文窗口小、记不住
       脚手架 · RAG 那一整套
       报废 · 2025 长上下文模型普及

2024   洞 · 工具调用不可靠
       脚手架 · 可视化工作流 n8n / Dify
       报废 · 2025 模型能可靠自调工具

2025   洞 · 长任务跑着会断
       脚手架 · 多 agent 并行编排
       报废 · 2026 一个长 agent 顶几十节点

图 2 · 每一层 harness 都对应模型当时的一个短板

2023 年模型的上下文窗口只有几千到几万 token，记不住跨会话的东西，于是有了 RAG 那一整套——文档切块、向量化、检索、重排序、查询改写——专门解决它装不下。

2024 年模型能调工具但调不稳，会写错参数、会在多步任务里跑丢目标，于是有了 n8n、Dify 这类可视化工作流，把流程画成节点图，让模型每个节点只做一件最小的事，流转由你写死的图保证。

Anthropic 2024 年 10 月发 Computer Use 时，自己都说这套能力时常笨拙、容易出错。

每一层都对着模型当时的一个洞。

而洞会被补上。

2025 年冬天模型能可靠地自己调工具了，那张精心画的节点图，就从替模型做决策，变成挡着模型做决策。

2026 年一个能跑长任务的 agent，自己就能完成 2024 年要几十个节点才拼得出来的流程——那几十个节点没变好也没变坏，它们变成了迁移时要清理的东西。

OpenAI 的研究科学家 Hyung Won Chung 有个说法，被 Lance Martin 引在那篇复盘里：在你当前的算力和数据水平上，该加的结构要加；但之后要把这些结构去掉，因为它们是捷径，会成为下一步提升的瓶颈。

Chung 说的是模型架构里那些手工设计的归纳偏置。

这句话挪到 agent harness 上，一个字都不用改。

加结构本身没有错——每一层结构当时都在补一个真实的洞。

错的是默认它会一直有用。

harness 组件的有效期，绑在模型的发布周期上：洞补上的那天，对应那层脚手架的价值就归零，然后它留在你的代码库里，等下一次升级，从帮手变成瓶颈。

所以加一层结构的时候，真正该一起记下来的，是它的临时性。

03

有一类脚手架不会过期

前两章讲的会折旧，只对一部分 harness 成立。

harness 这个词底下，装着两类性质完全不同的东西，把它们混在一起，是很多团队后来栽跟头的地方。

第一类，是前面说的能力脚手架：RAG、工作流编排、上下文压缩、工具调用的格式重试。

它们存在的理由是模型还做不到某件事。

模型做到了，它们就该退场。

这一类会折旧。

第二类，是给模型的自主行为划边界的东西：权限白名单、最小权限、危险操作的人工复核、审计日志、出问题能一键关停的开关，还有把 agent 接到公司内部系统上的集成代码。

工程师 Tian Pan 在一篇讲 agent 治理的文章里，把 agent 外面这层壳拆成执行层、协调层、治理层三层。

他有个观察值得抄下来：大多数 agent 上线失败，不是模型不够强，是它外面那层壳缺结构。

而治理这层结构有个麻烦的特点——它没法事后补。

给一个已经跑了几个月的生产系统补一套审计日志，是非常痛苦的事。

第二类 harness 不会随模型变强而贬值，原因正好相反：模型越强、越自主，它越要紧。

一个只按你画的节点图走的模型，你不太需要给它配审计——它每一步你都写死了。

一个能自己规划、自己调工具、自己连跑几小时的模型，你必须知道它做过什么，必须能在它做错时拦下来。

能力越大，边界越得清楚。

下一代模型不会让权限管理变得没必要，它让权限管理变得更必要。

能力脚手架（会折旧）
   解决 · 模型还做不到的事
   例子 · RAG、工作流编排、上下文压缩、重试
   规律 · 洞被补上,从帮手变成瓶颈
   建法 · 按随时能删来建

治理层（不折旧）
   解决 · 模型不该自己决定的边界
   例子 · 权限白名单、最小权限、审计、一键关
   规律 · 模型越自主越不可少
   建法 · 按长期基础设施来建

图 3 · 会折旧的能力脚手架，不会折旧的治理层

回头看 Lance Martin 删掉的东西，是第一类——为 2024 年模型短板搭的并行架构。

那套架构不是浪费。

它在 2024 年让 Open Deep Research 能用、能发布，是一笔花在当年、当年就回了本的开支。

2025 年它折旧到零，删掉就是了。

技术债不是指你当初搭了它，是指它过期了你还留着、还绕着它写代码、还不敢删。

这个两类的分法，有一派人根本不接受。

在他们看来，你这套能力脚手架会折旧、要趁早删的讲法本身就是错的——harness 不是模型的临时拐杖，harness 就是产品。

这一派里声音最大的是 LangChain。

他们开源了一套叫 Deep Agents 的东西，做法跟把 harness 做薄完全相反——把任务规划、子 agent 调度、中间件、钩子，全做进 harness 里，做厚。

他们的理由不弱。

在另一篇文章里他们讲得很清楚：模型变强，确实会把今天 harness 里的一些东西吸收进去；但这不意味着 harness 会变得不重要——就像今天 prompt engineering 仍然有用一样，harness engineering 也会一直有用，因为 harness 做的不只是补短板，它在系统性地组织模型的智能。

他们还有一个不容易反驳的观察：模型升级从来不会让 harness 这一层消失，它只会让旧的 harness 被新的 harness 替代——大模型外面永远需要一个系统。

这话有它的道理。

如果你真的相信 harness 会一直被需要、一直值得投入，那趁早删听上去就像短视。

但把这套反驳和前面那两类东西摆在一起看，分歧的位置就清楚了。

LangChain 说得对的那部分——harness 在组织智能、harness 永远会被需要——讲的是这一层作为整体不会消失，以及治理、编排这些组织性质的东西值得做厚。

这跟能力脚手架会折旧并不冲突。

会折旧的从来不是 harness 这一整层，是这一层里为某一代模型短板写的那些具体实现。

harness 不消失，和你 2024 年写的那套并行编排不消失，是两件事。

LangChain 自己那句话其实已经说明白了：旧 harness 被新 harness 替代——被替代掉的那个旧的，就是折旧。

所以这两派的分歧，不在做厚还是做薄，在你分不分得清手里这块 harness 是哪一类。

组织智能、划定边界的，做厚有道理。

补能力短板的，做厚就是给自己挖坑。

判断力就是这个——拿起一块 harness 代码，你知道它属于哪一类。

04

让框架变薄，让技能变厚

如果补能力短板的那类 harness 注定折旧，那写它的时候，就该让它好删。

怎么写才好删，有人已经想清楚，还给了它一个名字。

YC 的 CEO Garry Tan 在自己的一个仓库里写过一份设计信条，标题叫 Thin Harness, Fat Skills——薄 harness，厚技能。

一句话概括：把智能往上推，推进 skill 里；把执行往下推，推进确定性的工具里；中间那层 harness，保持薄。

具体说。harness 那层，按他的写法只有两百行左右，只干四件事：在一个循环里跑模型、管文件、控制上下文、做安全围栏。

判断、领域知识、业务流程，这些不写进 harness 代码，写成 skill——一份模型能直接读的 markdown。

这样拆，好处很直接。

下一代模型出来，你不用重写 harness。

skill 是模型读的，模型变聪明，同一份 skill 自动被执行得更好；harness 那两百行确定性代码本来不承载判断，不需要动。

Garry Tan 的原话是：模型一升级，每个 skill 立刻变好，因为隐含步骤里的判断力提升了，而确定性的步骤照旧可靠。

前面提过的 browser-use 团队，把这件事做到了一个挺极端的程度。

他们那套浏览器自动化 harness，核心大约六百行：一个十三行的 run.py 把东西跑起来，一个一百九十多行的 helpers.py 是对 Chrome 调试协议的薄封装，一个两百二十行的 daemon.py 保持连接不断，再加一个 SKILL.md 告诉模型这些怎么用。

它缺功能时的做法更值得看。

模型发现 helpers 里没有它要的某个函数，不会卡住——它像任何一个 Claude Code 用户那样，grep 一下 helpers.py，把函数补上，重跑。

harness 不预先把能力写全，它把补能力这件事交还给模型。

Gregor Zunic 那篇博客里有句话很干脆：你的 helpers 也是一种抽象，删掉它，让 agent 自己写它需要的。

这套东西的场景是浏览器自动化，封装的是 Chrome 协议，不能照抄到别的领域。

但薄框架、厚技能、模型自己补缺口这个形状是通用的。

薄不是省事，是把劲使对地方。

做薄之后省下来的工程力气，该花在模型真正的短板上。

Letta 这家公司——原来做 MemGPT 的那家——做了个叫 Letta Code 的编程 agent，主打持久记忆，让 agent 状态跨会话留存。

它是第三方 harness，不是模型厂自己做的。

在综合编程评测 Terminal-Bench 2.0 上，Letta Code 用 Claude Opus 4.5 拿到 59.1%；Anthropic 官方的 Claude Code 用同一颗 Opus 4.5 是 52.1%，换更新一代的 Opus 4.6 才追到 58.0%。

同一颗模型，一个把劲专门使在记忆上的第三方 harness，比模型厂的官方 harness 高出约七个百分点。

它赢，不是因为 harness 更厚、层数更多，是因为找准了一个模型的短板，在那一个点上做深。

会写 harness 的人值钱，这一点没有变。

变的是值钱的位置。

它不在你写下的那些代码能用多久——那些为某一代模型短板量身写的实现，会跟着模型一起折旧。

它在判断力：知道哪一层该薄、哪一层该厚，知道劲该使在模型的哪个短板上，知道一块 harness 过期了该果断删。

代码按模型周期折旧，判断力不折旧。

05

训练环境要宽，生产环境要窄

这一章是给做模型训练的人看的——具体说，给做 agent 强化学习、做 agent 后训练的人。

只用 agent、不训练它的读者，可以快速扫过。

机器人强化学习里有个反直觉的成熟做法。

要训一只机械手在真实世界里干活，你不会把仿真环境调得跟真实世界一模一样——你会反过来，把仿真里的纹理、光照、摩擦力、物体位置全部大幅随机化，让它宽到失真。

2017 年一篇提出 domain randomization（域随机化）的论文把这个做法的道理讲透了：仿真器里的多样性足够多时，真实世界对模型来说，不过是又一个变体。

反过来，一个调得又窄又精致的仿真环境，训出来的 policy（策略）一迈出仿真就废——这就是 sim-to-real gap。

训练环境要比部署环境宽，不是浪费，是模型能不能泛化的关键。

这件事搬到 agent 上，是一个很多团队会忽略的分野：训练用的 harness 和生产用的 harness，得朝相反的方向设计。

生产那套要窄。

一个对用户负责的线上系统，就该把 agent 能碰的工具限制到最小——严格白名单、最小权限、全程审计、出事一键关。

前一章讲的治理层，干的就是这个。

训练那套必须宽。

训练一个 agent，本质是让它在环境里反复试、反复错，学会判断：什么时候调哪个工具，工具失败了怎么恢复，任务跑偏了怎么自己拉回来。

这些判断，模型只能在一个足够宽的环境里长出来。

一份讲 agent 训练环境的分析里有句话很直接：只在单轮问答上训练的模型，一旦要它在五十步的企业工作流里保持状态，就会立刻吃力。

环境给模型多大的动作空间，它就只能在多大的范围里长出判断力。

于是有了那个最常见的错误：把生产环境那份窄白名单，原样搬进训练环境。

模型在那份只有五个工具的白名单里训练，它学到的是怎么在这五个工具里表现得好。

白名单之外的情况——一个没见过的工具、一个现有工具的升级版、一个该停下来问人的时刻——它没机会遇到，也就学不会处理。

ACL 2025 一篇叫 GenTool 的研究把这个机制坐实了：在固定工具集上微调，模型会过拟合到那些特定工具和用法，损害它对未见工具的泛化。

它学到的是这组工具怎么用，不是什么时候该用什么工具那种能迁移的判断。

这是工具微调场景的研究，但机制能类推到 agent 训练：你用一条软件工程的限制，替掉了模型本该自己长出来的判断。

你以为给训练环境加的是一道护栏，其实加的是一道天花板。

但训练要宽这句话，得防着被读成越宽越好。

宽是有代价的。

动作空间和环境越宽，探索效率越低、收敛越慢、样本越贵，模型还更容易学会钻奖励函数的空子——拿到高分却没真解决问题。

业界甚至有一整支研究在专门做反方向的事：怎么把动作空间缩小到模型训得动。

连 domain randomization 这个主张要宽的范式本身都承认：随机化的分布过宽，会带出根本不可行的解，反而让 policy 学不出来。

所以宽不是起点，是过程和终点。

前面那篇 domain randomization 的思路，到了 OpenAI 那个用机械手解魔方的项目里，变成一套叫 ADR 的机制：环境不是一上来就拉到最宽，而是从单一、不随机的环境起步，模型每达到一个性能阈值，就自动把随机化的范围加宽一档。

这跟强化学习里的 curriculum learning 是一个意思——从易到难分阶段推进，比一上来就最难收敛得更快、还更省样本。

训练环境的宽，是要一步步放开的宽，不是第一天就漫无边际的宽。

专门给别人做 agent 训练环境，这件事本身已经长成一个产业，多家研究机构和创业公司在做。

怎么设计训练环境的宽窄，正在变成一个独立的、要花钱买的能力。

把这两套 harness 搞反了，代价不会当场出现。

它会等到模型上线、遇到第一个白名单没覆盖的情况才暴露——而且是用你最不希望的方式：模型不会求助，也不会变通，它只会在它训练时待过的那个小笼子里，继续做笼子里的动作。

生产环境的窄，是为了上线那天安全。

训练环境的宽，是为了模型真的学会判断。

这一个窄和一个宽，不能是同一套东西。

06

把 harness 当成有保质期的东西

前面分了两类 harness、讲了薄和厚、讲了训练和生产。

这些分法落到日常，可以收成一个很小的检验。

模型升级那天，你打开代码库，要删掉一块过时的 harness。

如果这块删掉只花一个小时，你手里有的是一个选项。

如果要花一周，你手里有的是一笔债。

差别不在那块 harness 有多大，在你当初写它的时候，给没给它留下一条退出的路。

举两个具体的。

一种 harness，写成独立 skill 挂上去，或者做成一个组件、配置里一个开关就能整段摘掉——它跟别的部分之间只有一个清楚的接口。

模型升级让它没用了，你删一个文件、关一个开关，一个小时的事。

另一种 harness，是当初图省事，把逻辑直接焊进了主流程，中间还顺手跟另外十个组件勾连起来取数据、传状态。

它现在过时了，你想删，得先理清这十根线，每一根都可能在别处还有人用。

这就是那一周。

所以让 harness 好删，不是口号，是几个具体的习惯。

补能力短板的那类组件，单独成块，不要跟治理逻辑、跟业务主流程缠在一起——它们的折旧速度不一样，缠在一起，删得快的那个会被删得慢的那个拖住。

能做成 skill 的，不写进 harness 代码。

每加一层结构，顺手记一句：模型的哪个短板让我加了它。

等那个短板被下一代模型补上，这句话就是你的删除清单。

把补能力的那类 harness，当成一个有保质期的东西来对待。

不是说它明天就坏，是说你写它的那天，就该默认它活不久——下一代模型很可能让它过期——然后照这个默认来安排它的位置，让它到期那天好删。

一块好删的过期 harness，是一个选项；一块难删的过期 harness，是一笔你迟早要还的债。

这件事背后，是一个更老的规律。

2019 年，强化学习的奠基人之一 Rich Sutton 写过一篇很短的文章，叫《The Bitter Lesson》：七十年 AI 研究最大的一条教训是，靠人手把知识塞进系统的做法，短期有用，长期总会被那些利用大规模计算的通用方法赶过去。

1997 年打败卡斯帕罗夫的深蓝靠的是大规模搜索，不是把人对国际象棋的理解编进程序；二十年后计算机围棋又演了一遍。

这条规律值得知道，但要用得诚实——Sutton 讲的是研究在几十年尺度上的方向，不是你这个季度该怎么做产品。

一个要上线、要赚钱的产品等不起几十年，它现在就需要结构来兜底，也有人专门提醒过这条教训套到产品上的限度。

它对 harness 的意思不是现在就把结构删光，是给你一个方向感：你今天加的结构，是借来的时间。

所以下次你要给 agent 加一个 harness 组件，先别急着问它今天有没有用——能被你加进来的，今天大都有用。

问那个更难的问题：等模型升级、让这块组件变成多余的那天，你要花多久，才能把它干净地删掉。
