# 011 · 产品文档为什么总是过期 · notes

## 定位

报道 + 评判 + 可复用教程。不能只讲“文档变成代码的生成物”这个抽象趋势，读者看完要能重整自己的仓库，并生成一份带证据、可核对的说明。

过去，代码和文档是两份需要人工同步的系统描述。代码一改，README、API、架构图和使用说明就开始过期。AI 把代码翻译成自然语言的成本压到接近零后，这些描述系统现状的文档正在从人工维护的真源，变成根据代码按需生成的视图。

更深一层，代码也不是全部真相。人的意图、代码、测试、线上状态分别回答“为什么做、实现了什么、保证什么、实际启用什么”。未来的文档是这些真源面向不同读者的视图。AI 让写作成本趋近于零后，文档真正稀缺的部分变成证据和来源。

## 工作标题

产品文档为什么总是过期？AI 正在换一种写法

备选：

- 程序改了，说明书却还活在三天前
- 程序员终于不用追着代码改文档了

## 一句话钩子

照着一份只过期三天的文档开发，仍然可能多写一套保存逻辑、发不出第一张图片、误判用户数据是否隔离。AI 真正改变的不是写 README 的速度，而是描述系统现状的文字不必再靠人追着代码同步。

## 核心观点

AI 没有消灭文档，它把文档从另一份真相变成了证据的视图：

- 人的意图回答为什么做、不能做什么，由人维护。
- 代码回答系统具备哪些实现。
- 测试回答哪些行为正在被持续检查。
- 线上配置和监控回答此刻真正启用了什么。
- README、架构概览、接口说明和新人指南不再充当真源，而是从上述证据生成给不同读者看的视图。

代码作为主要技术真源不是新观点。AI 带来的新变化，是这些事实第一次可以被实时翻译成适合不同读者、不同任务的说明。生成成本降低后，文档的稀缺价值从“写得完整”转向“每句话能回到证据”。

## v6 内容反馈与结构重写

Joy 反馈：开头不应从“说明书过期”类比切入，而应先讲清过去几十年的软件协作方式；需要深入解释 PRD 为什么是给人看的、AI 如何改变交接关系、SDD 的价值与局限、文档和代码为什么会漂移，以及怎样建立更可靠的开发闭环。

v6 调整：

- 开头重写为完整的传统协作链：产品经理写 PRD 和原型，UI 补齐视觉与状态，前后端共同实现，测试按需求和设计验证。
- 提出核心判断：过去的产品文档是协作协议，依赖人的追问、经验、评审和会议补足空白；AI 时代，文档第一次成为可以直接产生代码的输入。
- 单设 SDD 章节，解释规格、设计、任务、实现的工作方式，同时写清“规格清晰不等于问题正确”“实现产生新知识”“多份文档扩大冲突面”“implement 不等于交付完成”四类局限。
- 把 Relio 三天漂移实验从文章开头移到论证中段，作为 SDD 局限的现实证据，不再让个案承担总论点。
- 解决方案从“代码生成文档”升级为四层证据与双向闭环：意图、规格、代码、测试和运行状态持续收敛。
- 新增两段可直接使用的提示词：开发前的 Feature Brief / 现状差异分析，以及实现后的规格—代码差异审计。
- 全文强调统一为普通粗体、浅灰高亮、下划线三层，避免整页处处加粗。

## 读者画像

工程师、技术负责人、技术 PM、独立开发者。维护过 README、接口文档、架构图，知道文档经常落后于实现；也正在使用 AI 理解或修改陌生代码库。

读者容易滑向两个极端：一是继续把所有文档当作需要人工维护的正式资产；二是认为 AI 能读代码后什么都不必写。这篇要把两者的边界说清楚。

## 待 verify 的事实清单

- DeepWiki 自动从仓库生成 wiki、架构图、摘要和源码链接的当前能力、时间与产品边界。
- GitHub Copilot 直接以仓库为上下文解释架构、入口和数据流的当前能力。
- GitHub 对 `AGENTS.md` / repository instructions 的要求，哪些信息仍需人工提供。
- Martin Fowler 2026 年 7 月关于 DSL、语义模型与“长期真源”的论证及原作者归属。
- SPDD 中从代码同步回结构化提示词的实际机制，避免把它写成单向的“文档生成代码”。
- “Code as Documentation” 的历史出处，明确本期的新意不是重复二十年前的观点。
- 代码生成文档的真实失败案例：幻觉、动态行为遗漏、跨仓库依赖、业务意图不可恢复、安全信息暴露。
- 至少一个真实仓库实验：AI 生成的架构说明与代码事实逐项对照，记录准确、遗漏和错误。

## 实验方向

选一个有真实业务逻辑、同时存在 README 或架构说明的代码仓库：

1. 不向 AI 提供现有文档，只提供代码。
2. 生成项目概览、关键入口、架构、数据流和运行方式。
3. 用代码、测试和现有文档逐项核对。
4. 把结果分成准确、遗漏、推断、错误四类。
5. 观察哪些内容能从代码恢复，哪些只能由人补充。
